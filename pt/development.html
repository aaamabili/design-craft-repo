Seção 10

Development

Publicar um web app de verdade, com contas, perfis compartilháveis e dados privados, sem vazar nada. HTTP, autenticação, Postgres e Row Level Security, as falhas do OWASP, segredos e infraestrutura, e a LGPD como requisito de produto, tudo em torno de um app concreto: uma wishlist.

Development · 01

How the Web Talks

Toda tela que você desenha é uma sequência de requisições HTTP. O método diz a intenção, o caminho diz o recurso, o status diz o que aconteceu. Ler isso na aba Network é a primeira habilidade de segurança, porque todo o resto é sobre quem pode mandar qual requisição.

Por quê

Um app de wishlist é um navegador conversando com uma API por HTTP. O navegador manda uma requisição com método, caminho, headers e às vezes um corpo; o servidor responde com um código de status, headers e um corpo, em geral JSON. Os métodos carregam significado: GET lê, POST cria, PATCH altera parte de algo, DELETE remove. Os códigos carregam o resultado: 200 ok, 201 criado, 204 feito sem nada para devolver, 400 você mandou algo errado, 401 você não está identificado, 403 você está identificado e mesmo assim não pode, 404 não está aqui, 429 devagar, 500 nós quebramos. A diferença entre 401 e 403 é a diferença entre autenticação e autorização, e ela aparece na aba Network muito antes de aparecer num design.

Os headers são onde mora o material de segurança interessante. A requisição carrega o token ou o cookie que identifica a pessoa; a resposta carrega as políticas que restringem o navegador. Abra o DevTools em qualquer app que você usa, filtre por Fetch/XHR e leia uma requisição de ponta a ponta. Você vai ver o que o app manda, o que recebe de volta, e o quão pouco a interface bonita tem a ver com o que o servidor de fato impõe. Uma regra para a seção inteira: nunca cole um token ou cookie real num print ou num chat. Trate como senha, porque é.

Como aplicar

  • Leia a aba Network do seu app uma vez por semana. Método, caminho, status, headers, corpo.
  • Use os métodos pelo significado. GET nunca altera dados; DELETE nunca finge ser POST.
  • Mapeie status para estados de UI: 401 vai para o login, 403 diz "não é seu", 404 diz "não há nada aqui", 429 pede para esperar.
  • Desenhe o diagrama React → Supabase (Auth, PostgREST, Storage) com cada seta rotulada pelo que carrega.

Detalhes que fazem a diferença

  • 401 e 403 são telas diferentes. Uma pergunta quem você é, a outra diz não.
  • 204 é sucesso com corpo vazio; não mostre erro porque o JSON veio vazio.
  • Idempotência: GET, PUT e DELETE podem repetir sem dano; POST não.
  • O corpo de um 4xx é para quem desenvolve; o texto da UI é seu.
  • Token em print é vazamento. Tarje antes de compartilhar.

Development · 02

What TLS Protects

HTTPS cifra a conversa entre navegador e servidor. Esconde o conteúdo e o caminho, verifica que você chegou ao servidor certo e impede adulteração em trânsito. Não faz nada por dados em repouso, nada contra uma página maliciosa e nada sobre quem o servidor deixa entrar.

Por quê

O Transport Layer Security embrulha o HTTP de modo que alguém na mesma rede, o provedor ou um proxy hostil vê só qual host você acessou e mais ou menos quanto dado passou. Headers, cookies, tokens, corpos de requisição e respostas estão todos dentro do túnel. O certificado prova que o servidor é quem o domínio diz, e é isso que derrota uma "página de login" falsa entre você e a real. Cloudflare Pages e Supabase dão isso por padrão, com certificados renovados para você; seu trabalho é nunca oferecer um caminho em HTTP puro e dizer aos navegadores para pararem de tentar, via HSTS.

Os limites importam tanto quanto as garantias. TLS protege bytes em movimento, não bytes guardados no banco, em backups ou numa linha de log. Não impede um script injetado na sua página de ler o que a página lê. Não decide se o usuário B pode ver a lista privada do usuário A; isso é autorização, dentro do túnel, decidida pelo servidor. "O site tem o cadeado" significa exatamente uma coisa: a rede entre a pessoa e o seu servidor não é o ponto fraco.

Como aplicar

  • HTTPS em tudo, sem exceção, incluindo a URL base da API na sua configuração.
  • Ative HSTS no projeto do Pages para que navegadores recusem HTTP puro depois da primeira visita.
  • Não confunda o cadeado com segurança. Ele cobre trânsito, não armazenamento, scripts ou permissões.
  • Conteúdo misto é quebra: uma imagem ou script em http numa página https enfraquece a página.

Detalhes que fazem a diferença

  • O que a rede ainda vê: o hostname (SNI), tempos e tamanhos.
  • Certificados expiram; plataformas gerenciadas renovam, self-hosted precisa de rotina.
  • HSTS preload é compromisso; adicione só quando todo subdomínio estiver pronto.
  • Dev local em http é ok; produção em http não.
  • TLS não é criptografia em repouso. Pergunte o que cifra o banco e os backups.
Fontes: MDN, Transport Layer Security · web.dev, Why HTTPS matters · MDN, Strict-Transport-Security · OWASP, TLS cheat sheet
Development · 03

Cookies, Sessions and Browser Storage

O navegador guarda estado em três lugares: cookies, que viajam com as requisições; localStorage e sessionStorage, que scripts leem; e memória, que some ao recarregar. Onde o token de sessão mora decide quais ataques podem roubá-lo.

Por quê

Sessão é o servidor lembrando quem você é entre requisições. O portador usual é um token, e o token precisa ser guardado em algum lugar do navegador. Cookies são enviados automaticamente em toda requisição ao seu domínio, o que é conveniente e também a raiz do CSRF; com a flag HttpOnly um script não consegue lê-los, a melhor defesa contra XSS roubar a sessão; com Secure só viajam por HTTPS; com SameSite deixam de ser anexados a requisições de outros sites. O localStorage é a troca oposta: nada é enviado automaticamente, então CSRF não se aplica, mas qualquer script rodando na página consegue ler, então um único buraco de XSS entrega todas as sessões.

O cliente de navegador do Supabase guarda a sessão em localStorage por padrão; configurações com renderização no servidor movem para cookies. As duas escolhas são defensáveis quando você sabe o que custam: com localStorage, XSS é o jogo inteiro e a Content Security Policy vira obrigatória; com cookies, SameSite e proteção contra CSRF viram obrigatórias. O que nunca é defensável é token em URL, token em log, ou token que nunca expira. Headers são o terceiro armazenamento que você não controla: o header Authorization é como o token chega à API a cada chamada, e a aba Network o mostra em texto claro para qualquer pessoa com o notebook aberto.

Como aplicar

  • Saiba onde sua sessão mora e escreva as defesas correspondentes: CSP para localStorage, SameSite e tokens de CSRF para cookies.
  • Cookies levam HttpOnly, Secure e SameSite por padrão, sempre.
  • Nada sensível no sessionStorage também; scripts leem, só dura menos.
  • Nunca token em URL. URLs acabam em logs, histórico e referrers.

Detalhes que fazem a diferença

  • HttpOnly é para o token, não para preferências. Tema pode morar em localStorage.
  • SameSite=Lax é o padrão sensato; Strict quebra links de e-mail, None exige Secure.
  • Logout precisa limpar o armazenamento, não só o estado da UI.
  • Computadores compartilhados: sessão persistida é decisão, ofereça "manter conectado" explicitamente.
  • Inspecione Application → Storage no DevTools para ver exatamente o que seu app deixa para trás.
Fontes: MDN, Using HTTP cookies · OWASP, Session management cheat sheet · OWASP, HTML5 security cheat sheet (local storage) · Supabase, Sessions
Development · 04

Same-Origin Policy and CORS

O navegador impede uma página de uma origem de ler respostas de outra. CORS é o servidor dizendo quais origens podem. Protege usuários de páginas maliciosas; não protege sua API de ninguém com curl.

Por quê

Origem é esquema mais host mais porta. A same-origin policy diz que um script em evil.example não pode ler a resposta de uma requisição à sua API, mesmo que o navegador a tenha enviado. É uma proteção do usuário: impede uma página aleatória de puxar seus dados logados através do seu próprio navegador. O CORS afrouxa isso de propósito: a API responde com Access-Control-Allow-Origin nomeando as origens que podem ler, e para requisições não simples o navegador manda antes um OPTIONS de preflight perguntando. O Supabase aceita chamadas de qualquer origem porque o portão de verdade é o token e a Row Level Security, não a origem.

O mal-entendido a matar cedo: CORS é imposto por navegadores, para navegadores. Um script, um app mobile, Postman ou curl o ignoram por completo. Se sua API só funciona porque "o frontend é a única coisa que chama", ela está aberta. Do mesmo modo, um Allow-Origin curinga com credenciais é uma configuração que o navegador recusa, e um Allow-Origin refletido (ecoando a origem que pediu) é porta aberta para os ataques que a política existe para impedir. A regra para a wishlist: assuma que todo endpoint será chamado diretamente, por qualquer um, e faça o banco dizer não.

Como aplicar

  • Trate CORS como cortesia do navegador, nunca como controle de acesso.
  • Permita origens específicas, nunca reflita a origem do pedido, nunca curinga com credenciais.
  • Todo endpoint precisa ser seguro chamado por curl com token roubado ou ausente.
  • Leia o preflight na aba Network uma vez, para o OPTIONS deixar de ser mistério.

Detalhes que fazem a diferença

  • Esquema, host, porta: https://app e http://app são origens diferentes.
  • Site versus origem: cookies SameSite usam o site; CORS usa a origem.
  • O preflight é cacheado; um OPTIONS falhando aparece como "network error" vago no console.
  • O Supabase ignora a origem por design; RLS é o portão.
  • Se remover o frontend expusesse dados, o backend nunca esteve protegido.
Fontes: MDN, Same-origin policy · MDN, Cross-Origin Resource Sharing · PortSwigger, CORS · web.dev, Same-site and same-origin
Development · 05

Authentication vs Authorization

Autenticação responde quem você é. Autorização responde o que você pode fazer. A maioria das violações reais é falha de autorização: o sistema sabia exatamente quem era a pessoa e mesmo assim entregou os dados de outra.

Por quê

Fazer login prova identidade: esta requisição vem da conta que sabe a senha, tem o magic link ou passou pelo segundo fator. Não diz nada sobre permissões. Autorização é a decisão separada, tomada a cada requisição, de que esta identidade pode ler esta lista, editar este item, excluir esta conta. As duas se confundem o tempo todo porque a tela de login é visível e a checagem de permissão não. O OWASP coloca Broken Access Control no topo da lista desde 2021 justamente porque times constroem fluxos de login lindos e depois confiam no frontend para esconder os botões que usuários não deveriam apertar.

Para a wishlist, o modelo de autorização é pequeno e precisa estar escrito: visitante lê listas públicas; pessoa logada lê listas públicas e tudo que possui; ninguém além do dono escreve. Essa matriz é a especificação. Ela é imposta no banco, via Row Level Security, para que todo caminho até os dados, o app, uma chamada direta à API, um futuro cliente mobile, obedeça às mesmas regras. Esconder um botão Editar é interface; negar o UPDATE é segurança. Os dois são necessários, nessa ordem de importância invertida.

Como aplicar

  • Escreva a matriz de permissões antes de escrever uma tabela: operação × papel, com Sim ou Não em cada célula.
  • Imponha no banco, reflita na UI. Nunca o contrário.
  • Autorize a cada requisição, não uma vez no login.
  • Teste como três pessoas: visitante, dono e outro usuário, para toda operação.

Detalhes que fazem a diferença

  • "Logado" não é permissão. É identidade.
  • Negar por padrão: tudo é proibido até uma regra permitir.
  • Dono é uma coluna, não um sentimento: user_id em toda linha que pertence a alguém.
  • Admin é um papel com auditoria própria, não uma senha compartilhada.
  • A matriz é o plano de testes. Cada célula é um teste.
Fontes: Auth0, Authentication vs. authorization · OWASP, Authorization cheat sheet · OWASP Top 10, A01 Broken Access Control
Development · 06

Sign Up, Sign In, Recover

Fluxos de conta são onde segurança e UX se encontram com mais força. Verificação de e-mail, regras de senha, links de recuperação e logout têm cada um uma forma correta, e o Supabase Auth implementa a maior parte, mas o produto ainda decide o que é exigido e o que a pessoa vê.

Por quê

Cadastro cria uma identidade; login prova; logout encerra a sessão; recuperação deixa alguém voltar sem a senha. Cada passo é superfície de ataque. E-mails não verificados permitem registrar endereços que a pessoa não possui, que depois viram forma de sequestrar contas ou enviar spam. Regras de senha fracas convidam credential stuffing; o conserto é tamanho mínimo, checagem contra senhas vazadas, e nenhuma regra de composição que produza "Senha1!". Recuperação é o buraco clássico: um link que nunca expira, que funciona mais de uma vez, ou que revela se um e-mail existe, entrega contas a atacantes. Logout que só limpa a UI deixa um token válido no aparelho.

O Supabase Auth dá cadastro com e-mail de confirmação, login por senha, magic links, provedores OAuth, recuperação de senha e gestão de sessão. As decisões que sobram são de produto: exigir verificação antes de qualquer escrita; mostrar a mesma mensagem neutra exista ou não o e-mail; expirar links de recuperação rápido e uma única vez; invalidar outras sessões na troca de senha; e fazer "Sair" revogar o refresh token, não só descartar o estado local. Documente o fluxo como diagrama com todo estado, inclusive os tristes, porque esse diagrama também é a especificação de UX.

Como aplicar

  • Exija verificação de e-mail antes de a conta poder criar ou compartilhar qualquer coisa.
  • Mensagens neutras: "Se esse e-mail existir, enviamos um link", para cadastro, recuperação e erro de login igualmente.
  • Links de recuperação expiram e são de uso único; troca de senha invalida outras sessões.
  • Sair revoga a sessão no servidor e limpa o armazenamento local.

Detalhes que fazem a diferença

  • Mínimo de 12 caracteres, sem regras de composição, checagem contra vazamentos conhecidos.
  • O e-mail de verificação é parte do produto: escreva, teste, dê marca.
  • SMTP próprio em produção; o remetente padrão tem limites estritos.
  • Destinos de redirecionamento em allowlist, nunca tirados de query string.
  • Duas contas de teste, sempre. Uma nunca basta para achar bug de autorização.
Fontes: Supabase, Auth overview · Supabase, Password-based auth · Supabase, Password security · OWASP, Forgot password cheat sheet · OWASP, Authentication cheat sheet
Development · 07

Tokens, JWTs and Expiry

Um JWT é uma afirmação assinada sobre quem é o portador, válida até expirar. Access tokens curtos limitam o dano de um roubo; refresh tokens estendem a sessão sem novo login. Assinado não é cifrado: qualquer um lê um JWT.

Por quê

Depois do login, o Supabase emite um access token, um JSON Web Token assinado pelo projeto, e um refresh token. O access token viaja em toda chamada à API no header Authorization; o Postgres lê suas claims, e é assim que auth.uid() sabe quem está pedindo. Ele expira em cerca de uma hora por padrão. Quando expira, o cliente usa o refresh token para obter um novo par, em silêncio. O desenho é uma troca: access tokens curtos fazem um token roubado servir por pouco tempo; refresh tokens evitam login a cada hora. A rotação de refresh token, ligada por padrão, torna cada refresh token de uso único, então um roubado que seja reusado depois de o cliente legítimo tê-lo usado derruba a sessão inteira.

Três fatos evitam a maioria dos erros com JWT. Um: o payload é base64, não cifrado, então nunca ponha segredos nele e assuma que a pessoa lê as próprias claims. Dois: o servidor não consulta o token num banco; verifica a assinatura, por isso revogar é difícil e a expiração é o controle real. Três: o segredo de assinatura e a chave service role são as chaves do reino; nunca saem do servidor. A expiração da sessão também é decisão de produto: uma wishlist não precisa de timeout de banco, mas "lembrar para sempre" num computador compartilhado é escolha consciente, com um jeito visível de sair de todos os aparelhos.

Como aplicar

  • Access tokens curtos, cliente renovando em silêncio, rotação ligada.
  • Nunca confie em claims do lado do cliente para permissões; o banco verifica a assinatura e aplica RLS.
  • Ofereça "sair de todos os aparelhos" e dispare isso na troca de senha.
  • Decodifique um token uma vez no jwt.io com conta de teste, para saber exatamente o que ele carrega.

Detalhes que fazem a diferença

  • exp é o controle. Todo o resto de um JWT é conveniência.
  • Rotação detecta reuso: refresh token repetido mata a sessão.
  • A claim role é "authenticated" ou "anon", não a flag de admin do seu app.
  • Desvio de relógio existe; não entre em pânico com um token rejeitado segundos antes.
  • Token em log é credencial em log. Limpe o header Authorization.
Fontes: Supabase, JSON Web Tokens · Supabase, User sessions · jwt.io, Introduction to JSON Web Tokens · PortSwigger, JWT attacks
Development · 08

Rate Limits, CAPTCHA, MFA and Redirects

Atacantes automatizam. Rate limits tornam adivinhar caro, CAPTCHA sobe o custo de bots onde a fricção vale a pena, MFA protege as contas que mais importam, e uma allowlist de redirecionamento impede seu login de virar lançador de phishing.

Por quê

Um formulário de login sem limites é um oráculo: tente um milhão de senhas, guarde as que funcionam. O Supabase aplica rate limits nos endpoints de auth e deixa ajustar; seu app também deve recuar no cliente, mostrar o 429 como "muitas tentativas, espere um minuto", e nunca revelar se o e-mail ou a senha era a metade errada. CAPTCHA, via provedores como o Cloudflare Turnstile, cabe no cadastro e na recuperação, onde bots criam contas lixo e disparam enxurradas de e-mail, e deve ficar fora do login diário a menos que apareça abuso, porque cada desafio é fricção paga por gente honesta.

Autenticação multifator é o maior upgrade para as contas que podem causar dano: a sua, como admin, e qualquer papel com direitos elevados. O Supabase suporta TOTP; exigir no login de admin custa segundos e tira a senha de ponto único de falha. Redirecionamentos são o item silencioso: fluxos de auth mandam a pessoa de volta a uma URL depois do login ou da recuperação, e se essa URL vem da requisição, um link forjado loga alguém no seu site real e a deixa numa página do atacante. O Supabase só redireciona para URLs registradas; mantenha a lista curta e nunca adicione a ela a partir de entrada do usuário.

Como aplicar

  • Rate limits no auth e em todo endpoint que envia e-mail; mostre 429 como um "espere" calmo.
  • CAPTCHA no cadastro e na recuperação, não em todo login, a menos que veja abuso.
  • MFA obrigatório para contas admin, opcional para as outras, com códigos de recuperação.
  • Só allowlist de redirecionamento. Sem open redirect, sem redirecionamento vindo de query string.

Detalhes que fazem a diferença

  • Mesmo erro para e-mail errado e senha errada. Enumeração começa com uma mensagem prestativa.
  • Bloqueio de conta é vetor de negação de serviço; prefira backoff a travas rígidas.
  • Turnstile em vez de quebra-cabeças de imagem: invisível para a maioria, caro para bots.
  • Admin é uma história de login separada, com MFA e log de auditoria próprio.
  • Teste um redirecionamento forjado uma vez para ver a allowlist recusar.
Fontes: Supabase, Rate limits · Supabase, Bot detection with CAPTCHA · Supabase, Multi-factor authentication · Supabase, Redirect URLs · OWASP, Unvalidated redirects cheat sheet · Cloudflare Turnstile
Development · 09

Modeling Profiles, Lists and Items

Três tabelas carregam a wishlist: profiles, wishlists, wishlist_items. Chaves estrangeiras tornam as relações reais, constraints tornam dados ruins impossíveis, e a coluna de dono em toda linha é o que a Row Level Security vai checar depois. Modele para as permissões que vai precisar.

Por quê

O Supabase mantém a autenticação em auth.users, que você não edita diretamente. O perfil público (nome de exibição, handle, avatar) mora numa tabela profiles com o mesmo id, criada por um trigger quando alguém se cadastra. Wishlists referenciam o perfil por uma chave estrangeira user_id e carregam uma coluna de visibilidade; itens referenciam sua wishlist. Chaves estrangeiras com ON DELETE CASCADE fazem excluir uma conta remover suas listas e itens, o que é limpo e, como as aulas de LGPD vão mostrar, uma necessidade legal. Constraints fazem o resto da higiene: NOT NULL onde o valor é obrigatório, UNIQUE no handle, CHECK na visibilidade para só existirem os três valores permitidos, e limite de tamanho nos títulos para ninguém guardar um romance.

Índices deixam as consultas comuns rápidas: wishlists por user_id, itens por wishlist_id, perfis por handle. Chaves primárias em UUID em vez de inteiros sequenciais fecham o ataque mais barato que existe, adivinhar o próximo id, embora UUID não substitua autorização. Escreva o esquema como migrações SQL no repositório, não como cliques num painel; SQL versionado é o que permite reconstruir o banco, revisar uma mudança e saber qual política existia quando.

Como aplicar

  • profiles(id → auth.users), wishlists(user_id, visibility), wishlist_items(wishlist_id). Coluna de dono em tudo que tem dono.
  • Constraints antes de código: NOT NULL, UNIQUE, CHECK, limites de tamanho.
  • Chaves primárias UUID, e índice em toda chave estrangeira usada em filtro.
  • Migrações no git. O painel é para ler, o repositório é a verdade.

Detalhes que fazem a diferença

  • Nunca guarde o e-mail em profiles a menos que precise dele público; auth.users já o tem.
  • CASCADE é decisão de design; escreva o que desaparece junto com a conta.
  • Timestamps com fuso, created_at e updated_at em toda tabela.
  • Visibilidade como CHECK constraint, não string livre.
  • Popule com dados fictícios e mantenha um script para resetar.
Fontes: Supabase, Managing user data · PostgreSQL, Constraints · PostgreSQL, Indexes · Supabase, Cascade deletes · PostgreSQL, Tutorial
Development · 10

Row Level Security

RLS transforma autorização em regras do banco: cada tabela ganha políticas que dizem quais linhas um usuário pode selecionar, inserir, atualizar ou excluir. Com auth.uid() na política, o próprio banco recusa o que a pessoa não pode, seja quem for e de onde for.

Por quê

O Supabase expõe suas tabelas por uma API que o navegador chama diretamente com o token da pessoa. Isso só funciona porque Row Level Security está ligada: uma tabela sem RLS e com a chave anon no cliente é pública para o mundo. Com RLS ativa, o Postgres avalia uma política para cada linha em cada operação. A política pode ler auth.uid(), o id do token verificado, e comparar com a coluna de dono. Uma política por operação mantém a lógica legível: SELECT permite donos e, para listas públicas, todo mundo; INSERT checa que o user_id da linha nova é quem chama; UPDATE e DELETE permitem só o dono. Políticas são aditivas: se qualquer uma permite, a linha passa, então uma permissiva esquecida de testes é um buraco.

Duas práticas mantêm a RLS honesta. Primeira, teste de fora da UI: rode a mesma consulta como visitante sem token, como usuário A, como usuário B, pela API, e compare as linhas. Segunda, mantenha as políticas em migrações e revise como código, porque política é código. Performance vem junto: embrulhe auth.uid() num subselect para ser avaliado uma vez, indexe as colunas que as políticas comparam, e evite joins dentro de políticas. Os advisors do Supabase apontam tabelas sem RLS e políticas que parecem erradas; rode antes de todo release.

Como aplicar

  • ALTER TABLE … ENABLE ROW LEVEL SECURITY em toda tabela, antes da primeira linha.
  • Uma política por operação, nomeada pelo que permite: "donos atualizam suas wishlists".
  • INSERT usa WITH CHECK para ninguém criar linhas de outro dono.
  • Teste pela API como três pessoas e guarde os resultados numa tabela no repositório.

Detalhes que fazem a diferença

  • Sem RLS mais chave anon é tabela pública. Não há meio-termo.
  • Políticas são somadas com OU. Apague a "permite tudo para teste".
  • (select auth.uid()) em vez de auth.uid() para velocidade em tabelas grandes.
  • service_role ignora RLS, por isso nunca chega ao cliente.
  • Views e funções precisam de pensamento próprio; funções security definer pulam a RLS.

Public, Unlisted, Private

Uma wishlist tem três públicos: qualquer um, qualquer um com o link, só o dono. Cada nível é uma política no banco e uma frase na interface. Se a frase promete mais do que a política impõe, o produto está mentindo.

Por quê

Listas públicas aparecem na busca e no perfil; listas não listadas abrem para quem tem a URL mas não aparecem em lugar nenhum; listas privadas são só do dono. A diferença é trivial na UI e decisiva no banco. Pública: SELECT permitido para todos onde visibility = public. Não listada: SELECT permitido para todos por id, mas a consulta que alimenta a página de perfil as exclui, então descobrir depende de saber o UUID, por isso o id precisa ser inadivinhável. Privada: SELECT só para o dono. Itens herdam a visibilidade da lista por uma política que faz join com o pai, ou por uma coluna desnormalizada mantida em sincronia por trigger.

A interface precisa dizer exatamente o que cada nível significa, onde a pessoa escolhe, em palavras simples: "Qualquer um pode encontrar esta lista", "Só quem tem o link", "Só você". O princípio da transparência da LGPD torna isso mais que boa educação. E o padrão importa: uma lista nova deve ser privada até a pessoa decidir o contrário, porque uma lista pública por acidente é um vazamento que a pessoa não consentiu. Teste os níveis como um atacante: busque uma lista não listada por id sem token, liste as listas de um perfil e confira que as não listadas estão ausentes, busque uma privada como outro usuário e espere nada de volta.

Como aplicar

  • Três valores, uma CHECK constraint, três políticas. Nenhum outro estado.
  • Privada por padrão. Compartilhar é ação que a pessoa toma.
  • Rótulos em linguagem simples no controle, não numa página de ajuda.
  • Itens seguem a lista; nunca deixe um item mais visível que o pai.

Detalhes que fazem a diferença

  • Não listada significa inadivinhável: ids UUID v4, nenhum número sequencial em lugar nenhum.
  • Mudar para privada vale na hora, incluindo páginas em cache e imagens.
  • A busca indexa só listas públicas; não listadas nunca vazam pela busca.
  • O diálogo de compartilhar repete a visibilidade no momento de copiar o link.
  • URLs de imagem seguem o nível também; lista privada com imagem pública não é privada.
Fontes: Supabase, Row Level Security · OWASP, Authorization cheat sheet · ANPD, materiais educativos

Broken Access Control and IDOR

Troque o id na URL e veja os dados de outra pessoa: isso é uma Insecure Direct Object Reference, o bug sério mais comum da web. O conserto nunca é esconder o id; é fazer toda consulta checar propriedade, o que a RLS faz se as políticas estão certas.

Por quê

O OWASP coloca Broken Access Control em primeiro porque está em todo lugar e é simples: o app checa quem você é, busca o registro que você pediu, e esquece de checar se o registro é seu. A versão de API se chama BOLA, Broken Object Level Authorization. Sintomas: mudar /lists/42 para /lists/43 mostra a lista privada de outra pessoa; um PATCH no item de outro usuário dá certo; um endpoint de exportação devolve os dados de todo mundo porque o filtro era aplicado no frontend. Ids inadivinháveis atrasam isso e não consertam; um atacante que viu um id uma vez, num link compartilhado ou num print, o tem para sempre.

A defesa é estrutural. Com RLS ligada e correta, a consulta que busca a lista 43 devolve nada para o usuário errado, mande o frontend o que mandar. O trabalho que sobra é testar: para cada operação da matriz de permissões, execute como o usuário errado pela API e confirme a recusa. Guarde um documento desses testes com a requisição, o resultado esperado e o obtido; é a evidência de que seu controle de acesso funciona, e a primeira coisa a rodar de novo depois de qualquer mudança de esquema. Vigie também os caminhos de segunda ordem: joins que puxam linhas relacionadas, funções que rodam com direitos elevados, e arquivos no storage cujas URLs pulam o banco por completo.

Como aplicar

  • Toda busca de objeto é filtrada por propriedade ou visibilidade, no banco.
  • Teste troca de id em todo endpoint, como visitante e como outro usuário.
  • Ids inadivinháveis são cortesia, não controle.
  • Mantenha o log de testes ofensivos ao lado do esquema e rode de novo a cada mudança.

Detalhes que fazem a diferença

  • Negar por padrão devolve vazio ou 404, não 403 com o nome do objeto.
  • Mass assignment é o primo: nunca deixe o cliente definir user_id ou visibilidade na linha de outro.
  • Endpoints em lote filtram por linha, não por requisição.
  • Funções SECURITY DEFINER precisam de checagem de propriedade própria.
  • Automatize o teste de três usuários depois que funcionar à mão.

XSS and Safe Rendering

Cross-site scripting é conteúdo de usuário executando como código no navegador de outro usuário. A defesa é renderizar texto como texto: o React faz isso por padrão, dangerouslySetInnerHTML desfaz, e uma Content Security Policy pega o que escapar.

Por quê

Uma wishlist guarda texto que as pessoas digitam: nomes de itens, notas, bios de perfil, URLs. Se qualquer parte disso entra na página como HTML, uma nota contendo uma tag script roda no navegador de todo mundo que vê a lista, com a sessão de cada um. Isso é XSS armazenado, e com a sessão em localStorage é fim de jogo para todo visitante. O React escapa texto no JSX, então o caminho comum é seguro; os buracos são as saídas de emergência: dangerouslySetInnerHTML, escrever em innerHTML, montar strings de HTML, e atributos que recebem URLs, onde links javascript: executam no clique. Renderização de Markdown é fonte clássica, porque o renderizador produz HTML a partir de texto não confiável.

As regras são curtas. Nunca renderize conteúdo de usuário como HTML a menos que tenha passado por um sanitizador como o DOMPurify com allowlist de tags. Valide URLs antes de usar como href ou src: só http e https, nada mais. Defina uma Content Security Policy que proíba scripts inline, para que mesmo uma tag injetada não rode. E teste com os payloads que importam: uma tag script, um img com onerror, uma URL javascript:, um svg com onload, em todo campo que depois é exibido. Codificação de saída é contextual, por isso "escapar tudo" não é estratégia; o contexto (texto HTML, atributo, URL, JavaScript) decide a codificação.

Como aplicar

  • Texto continua texto. Nada de dangerouslySetInnerHTML com conteúdo de usuário, nunca.
  • Sanitize com allowlist se precisar renderizar texto rico; DOMPurify, não regex.
  • Permita só http(s) em URLs digitadas; renderize o resto como texto simples.
  • CSP sem unsafe-inline como segunda camada.

Detalhes que fazem a diferença

  • Markdown é HTML com passos extras; sanitize depois de renderizar.
  • Teste campos com <img src=x onerror=alert(1)> e um link javascript:.
  • DOM XSS mora no cliente: location.hash em innerHTML é clássico.
  • rel="noopener" em links para URLs fornecidas por usuários.
  • Scripts de terceiros compartilham sua origem; carregue o mínimo possível.

SQL Injection

Injeção acontece quando dado é colado numa consulta como texto e o banco o lê como código. Consultas parametrizadas mantêm os dois separados. O cliente do Supabase e o PostgREST parametrizam por você; o risco volta no momento em que você monta strings de SQL.

Por quê

O ataque tem quarenta anos e continua na lista do OWASP porque concatenar strings é fácil. Uma caixa de busca que vira WHERE title = '… transforma uma aspa simples num jeito de encerrar a string e escrever mais SQL: ler outras tabelas, pular um login, derrubar uma tabela. A defesa não é escapar aspas; é nunca misturar dado ao texto da consulta. Consultas parametrizadas enviam o SQL e os valores separados, então o banco trata o valor como valor, sejam quais forem os caracteres. O cliente JavaScript do Supabase monta requisições parametrizadas, e o PostgREST faz o mesmo no servidor, então o caminho comum é seguro.

Os buracos aparecem onde você escreve SQL: funções do banco que montam consultas dinâmicas por concatenação, chamadas RPC que recebem fragmentos crus, Edge Functions que falam direto com o Postgres, e scripts de admin. Em funções Postgres use format() com %L e %I, ou EXECUTE … USING, nunca || com entrada de usuário. Validação de entrada ajuda por sanidade (número de página é número) mas não é a defesa; uma string de aparência válida ainda pode ser injeção. Teste com os payloads clássicos em toda entrada que chega a uma consulta e observe erros que vazam a consulta, o que por si já é divulgação de informação.

Como aplicar

  • Parâmetros, nunca concatenação, em todo lugar que toca SQL.
  • Em funções Postgres, format() com %L/%I ou EXECUTE … USING.
  • Usuário de banco com privilégio mínimo para qualquer código de servidor que você escreva.
  • Mensagens de erro para usuários são genéricas; o erro real vai para o log.

Detalhes que fazem a diferença

  • Teste com ' OR 1=1 -- e uma aspa em todo campo.
  • ORMs e clientes são seguros até você chamar .raw() ou montar uma string de filtro.
  • Nomes de coluna e tabela não são parâmetros; use allowlist.
  • Entradas de busca full-text também passam por parâmetros.
  • Um erro vazado com SQL dentro é um achado por si só.

CSRF and When It Applies

Cross-site request forgery é outro site fazendo o navegador mandar uma requisição ao seu com os cookies do usuário anexados. Só funciona quando a credencial viaja automaticamente. Saiba qual modelo você usa, depois aplique a defesa correspondente.

Por quê

Cookies são anexados às requisições pelo navegador, seja qual for a página que as iniciou. Um formulário escondido em evil.example que faz POST na sua API chegaria carregando o cookie de sessão da vítima, e o servidor acreditaria. Isso é CSRF. As defesas são cookies SameSite, que impedem o navegador de anexar cookies a requisições de outros sites, tokens anti-CSRF que o atacante não conhece, e checagem do header Origin. Se em vez disso o token de sessão mora em localStorage e é enviado como header Authorization pelo seu próprio JavaScript, uma página estranha não consegue adicionar esse header, e CSRF não se aplica; o preço, como a aula de armazenamento disse, é que XSS vira o jogo inteiro.

O cliente de navegador padrão do Supabase usa o modelo de header, então uma wishlist simples construída nele não está exposta a CSRF. No momento em que você move a sessão para cookies, para renderização no servidor ou para um backend próprio, o CSRF volta e SameSite=Lax mais checagem de origem viram obrigatórios. Lembre também das variantes sem cookie: uma ação logada disparada por GET (um link de "descadastrar" ou "excluir") é forjável a partir de uma tag de imagem, mais um motivo para GET nunca mudar estado. Decida o modelo, escreva, e teste: um formulário em outra origem fazendo POST na sua API deve falhar.

Como aplicar

  • Token em header: sem CSRF, CSP obrigatória. Token em cookie: SameSite mais tokens ou checagem de origem.
  • Requisições que mudam estado nunca são GET.
  • Cheque Origin ou Referer no servidor quando cookies são a credencial.
  • Teste de uma página estranha uma vez; espere a requisição recusada.

Detalhes que fazem a diferença

  • SameSite=Lax ainda envia cookies em navegação GET de nível superior; por isso GET precisa ser seguro.
  • CORS não previne CSRF; a requisição é enviada, só a resposta é escondida.
  • Login CSRF também existe: logar a vítima na conta do atacante.
  • Double-submit cookie é o esquema de token mais simples para um app pequeno.
  • Documente o modelo de sessão para a próxima pessoa aplicar a defesa certa.
Fontes: PortSwigger, CSRF · OWASP, CSRF prevention cheat sheet · MDN, SameSite cookies · web.dev, SameSite cookies explained

Keys and Secrets

A chave anon foi feita para ser pública e é inútil sem RLS. A chave service role ignora a RLS e nunca pode sair de um servidor. Variáveis de ambiente, .gitignore e varredura de segredos mantêm a segunda fora do bundle e do repositório.

Por quê

O Supabase dá a todo projeto dois tipos de chave. A publishable ou anon identifica o projeto e vai no navegador; seu único poder é chamar a API como usuário anônimo ou autenticado, que a RLS então restringe. A secret ou service role é a chave mestra: ignora toda política e lê e escreve qualquer coisa. Ela pertence a um ambiente de servidor, uma Edge Function ou um script confiável, nunca a código de frontend, nunca a uma variável Vite com prefixo VITE_, porque tudo com esse prefixo é compilado no bundle público. Uma chave service role num bundle JavaScript é igual a um banco público.

Segredos chegam ao repositório por descuido: um .env commitado sem querer, uma chave colada num arquivo de configuração, um print na documentação. As defesas são rotina: .env no .gitignore desde o primeiro commit, um .env.example com placeholders, varredura de segredos do GitHub ligada, um scanner local como o gitleaks num hook de pre-commit, e rotação no momento em que uma chave é suspeita de ter vazado, porque o histórico do git lembra de tudo. O Cloudflare Pages guarda variáveis de produção no painel, separadas dos ambientes de preview, e é aí que a divisão dev/prod começa a importar.

Como aplicar

  • Chave anon no cliente, service role nunca. Sem prefixo VITE_ em nada secreto.
  • .env ignorado, .env.example commitado, variáveis definidas no painel da hospedagem.
  • Varredura de segredos no repositório e um scanner de pre-commit local.
  • Rotacione na suspeita, não na prova. Chave vazada é vazada para sempre no histórico.

Detalhes que fazem a diferença

  • Procure "service_role" no bundle compilado antes de todo deploy. Leva dez segundos.
  • Chaves diferentes por ambiente; chave de staging vazada não pode abrir produção.
  • Rotação é treino: pratique antes de precisar.
  • Prints do painel frequentemente contêm chaves. Recorte.
  • A chave anon é pública por design; pare de tratá-la como segredo e passe a tratar a RLS como a fechadura.

Storage, Uploads and Signed URLs

Imagens de presentes são arquivos, e arquivos têm permissões próprias. Buckets são públicos ou privados, políticas decidem quem envia e quem lê, URLs assinadas dão acesso temporário a arquivos privados, e limites de tamanho e tipo impedem uploads de virarem ataque.

Por quê

O Supabase Storage guarda arquivos em buckets com políticas no estilo RLS sobre a tabela de objetos. Um bucket público serve qualquer arquivo por URL, para sempre, a qualquer um; isso é certo para avatares e errado para imagens numa lista privada. Um bucket privado serve arquivos só por requisições autenticadas ou URLs assinadas, links que expiram depois de um tempo definido. A wishlist precisa dos dois: bucket público para fotos de perfil, bucket privado para imagens de itens, com políticas que espelham a visibilidade da lista, para que as imagens de uma lista privada não vazem por uma URL copiada uma vez. Convenções de caminho ajudam: user_id/list_id/arquivo, com políticas que comparam a primeira pasta com auth.uid().

Upload é entrada. Limite tamanho por arquivo e por bucket, restrinja tipos MIME às imagens que você de fato exibe, e nunca confie na extensão; o servidor decide o tipo de conteúdo. Renomeie arquivos no upload para os caminhos não serem controlados pelo usuário, o que fecha truques de path traversal e sobrescrita. Remova metadados EXIF se localização puder vazar. E considere o que acontece ao excluir: remover um item deve remover sua imagem, ou você segue pagando por, e potencialmente servindo, arquivos que deveriam ter sumido, o que a LGPD vai cobrar.

Como aplicar

  • Bucket público para avatares, privado para imagens de lista, políticas espelhando a visibilidade.
  • URLs assinadas com expiração curta para tudo que é privado; nunca link permanente.
  • Limites de tamanho e MIME no bucket, nomes gerados pelo servidor, sem caminhos de usuário.
  • Exclua arquivos junto com as linhas, e teste que uma imagem excluída para de ser servida.

Detalhes que fazem a diferença

  • URLs de bucket público são cacheáveis para sempre; mover a lista para privada não as recolhe.
  • Caminhos pasta-por-usuário deixam políticas de propriedade numa linha.
  • Transformações de imagem no servidor também removem conteúdo perigoso.
  • Uploads de SVG podem carregar scripts; trate como código, não como imagem.
  • Teste os três usuários em arquivos também, não só em linhas.

Security Headers and CSP

Um punhado de headers de resposta diz ao navegador como proteger sua página: quais scripts podem rodar, se ela pode ser emoldurada, como referrers vazam, quais recursos são permitidos. A Content Security Policy é o mais pesado e o mais valioso, porque amortece XSS mesmo quando existe um buraco.

Por quê

O navegador faz muito por você se pedido. Content-Security-Policy lista de onde scripts, estilos, imagens e conexões podem vir; uma política estrita sem unsafe-inline faz uma tag script injetada simplesmente não rodar. Strict-Transport-Security fixa HTTPS. X-Content-Type-Options impede sniffing de MIME. X-Frame-Options ou frame-ancestors impede seu login de ser emoldurado numa página de clickjacking. Referrer-Policy impede URLs completas, que podem conter ids de listas não listadas, de vazarem para outros sites. Permissions-Policy desliga câmera, geolocalização e afins que você não usa. O Cloudflare Pages define tudo isso por um arquivo _headers na saída do build.

CSP é o que dá trabalho, porque um app Vite com cliente Supabase, Google Fonts e um script de analytics tem fontes reais para declarar, e estilos inline de bibliotecas brigam com um style-src estrito. Comece em modo report-only, leia as violações, aperte, depois imponha. O connect-src precisa incluir sua URL do Supabase; img-src precisa incluir o domínio do storage; script-src deve ser sua origem mais hashes ou nonces, nada inline. Teste com o securityheaders.com e com o console aberto. A recompensa é que o pior caso da aula de XSS, um script numa nota, vira uma requisição bloqueada em vez de uma sessão roubada.

Como aplicar

  • Arquivo _headers no Pages com HSTS, nosniff, frame-ancestors, Referrer-Policy, Permissions-Policy.
  • CSP em report-only primeiro, depois imposta, sem unsafe-inline para scripts.
  • Declare só o que usa: sua origem, Supabase, fontes.
  • Reconfira os headers depois de toda mudança de infra com um scanner externo.

Detalhes que fazem a diferença

  • Referrer-Policy: strict-origin-when-cross-origin mantém ids não listados fora dos logs de outros sites.
  • frame-ancestors 'none' a menos que você embuta de propósito.
  • Nonces ou hashes para o único script inline que não dá para evitar.
  • Report-only não é proteção; marque uma data para impor.
  • Headers são por resposta; cheque a API e o domínio do storage também, não só a página.
Fontes: MDN, Content Security Policy · web.dev, Strict CSP · OWASP, HTTP headers cheat sheet · Cloudflare Pages, Headers · securityheaders.com

Dependencies and the Supply Chain

Seu app é majoritariamente código dos outros. Um pacote vulnerável entrega sua vulnerabilidade; um pacote sequestrado entrega o malware de alguém. Lockfiles, auditorias, atualizações automáticas e o hábito de ler o que instala são os controles.

Por quê

Um projeto Vite com React puxa centenas de pacotes, cada um um buraco em potencial e cada um um caminho possível para uma atualização maliciosa. O OWASP lista componentes vulneráveis e desatualizados no Top 10; os incidentes de supply chain dos últimos anos acrescentaram typosquatting e sequestro de contas de mantenedores à lista. A base é mecânica: commite o lockfile para instalações serem reproduzíveis, rode npm audit no CI e leia o resultado, ligue o Dependabot ou equivalente para atualizações chegarem como pull requests revisáveis, e fixe versões maiores de tudo que toca autenticação ou renderização. A parte de julgamento é ler: antes de adicionar um pacote, veja manutenção, downloads, árvore de dependências e se você precisa mesmo dele.

Código de frontend roda no navegador do usuário com a sessão do usuário, então uma biblioteca de UI comprometida é tão perigosa quanto um backend comprometido. Mantenha a lista de dependências curta, prefira recursos da plataforma a pacotes para necessidades pequenas, e evite pacotes que puxam dezenas de outros por uma função. Atualizações agendadas e chatas vencem as heroicas: uma janela mensal em que tudo avança um pouco é mais segura que um salto anual que quebra o build. Quando sair uma vulnerabilidade em algo que você usa, saiba em um dia, não num trimestre.

Como aplicar

  • Lockfile commitado, npm audit no CI, falhas triadas na mesma semana.
  • PRs automáticos de atualização com cadência regular de merge.
  • Leia antes de instalar: mantenedores, atividade, tamanho, dependências transitivas.
  • Menos pacotes: cada dependência é uma decisão permanente de confiar num estranho.

Detalhes que fazem a diferença

  • npm audit fix --force pode quebrar coisas; leia o diff.
  • Dependências de dev rodam na sua máquina; scripts postinstall também são vetor.
  • Fixe pelo lockfile, não por versões exatas no package.json, para patches continuarem fluindo.
  • Assine os avisos dos cinco pacotes que mais importam.
  • Remova o que parou de usar; pacote sem uso ainda é instalado e ainda é hackeado.
Fontes: OWASP Top 10, A06 Vulnerable and Outdated Components · npm, npm audit · GitHub, Dependabot · OWASP, Vulnerable dependency management cheat sheet

Logs, Backups and Environments

Não se defende o que não se vê nem se restaura. Logs dizem que algo aconteceu, alertas dizem agora, backups deixam desfazer, e um teste de restauração prova que o backup é real. Ambientes separados mantêm experimentos longe dos dados de pessoas reais.

Por quê

Falhas de log e monitoramento são uma categoria própria do OWASP porque violações passam meses sem serem notadas. Para um app pequeno a régua é modesta e ainda assim real: o Supabase guarda logs de auth, API e banco; leia quando algo estiver estranho, e configure alertas para os eventos que importam, rajadas de login falho, erros disparando, volumes incomuns de leitura. Registre o que aconteceu e quem fez, nunca o que a pessoa digitou num campo de senha nem o token que carregava. Logs também são dado pessoal sob a LGPD, então ganham prazo de retenção como tudo mais.

Backups são a diferença entre um incidente e uma catástrofe. O Supabase faz backups diários nos planos pagos, com recuperação pontual disponível; o plano gratuito não, e isso é motivo para decidir cedo o que perder tudo significaria. Um backup que ninguém restaurou é esperança, não controle; agende uma restauração num projeto descartável e cronometre. Ambientes completam o quadro: desenvolva contra um projeto separado com dados fictícios, use deploys de preview para revisão, e mantenha chaves de produção só em produção. O branching do Supabase e os previews do Cloudflare tornam a divisão barata; a disciplina é nunca apontar um build de dev para o banco de produção "só um minuto".

Como aplicar

  • Leia os logs semanalmente, alerte para rajadas de login falho e picos de erro.
  • Backups ligados, restauração testada ao menos uma vez antes do lançamento e depois de mudanças grandes.
  • Projetos separados para dev e prod, dados fictícios em dev, previews para revisão.
  • Logs têm retenção, e nunca contêm senhas ou tokens.

Detalhes que fazem a diferença

  • Cronometre o treino de restauração e anote quanto tempo levou.
  • Fadiga de alerta é modo de falha; três alertas que importam vencem trinta.
  • Limpe headers Authorization e e-mails de qualquer coisa que mande a um logger de terceiros.
  • Quem tem acesso a produção? Escreva a lista; mantenha curta.
  • Migrações rodam em dev primeiro, depois preview, depois prod, com plano de rollback.

Personal Data Under the LGPD

A Lei Geral de Proteção de Dados se aplica no momento em que você guarda um nome ou um e-mail. Ela define dado pessoal e dado sensível, nomeia os papéis de controlador e operador, e fixa princípios que se leem como requisitos de produto: finalidade, necessidade, transparência, segurança.

Por quê

Dado pessoal é qualquer coisa que identifica ou pode identificar uma pessoa natural: nome, e-mail, handle, foto, endereço IP, id de dispositivo, e a combinação de campos inofensivos que juntos apontam para alguém. Dado sensível é um conjunto mais estreito com regras mais duras: saúde, orientação sexual, religião, etnia, política, biometria, genética. Uma wishlist parece inofensiva até você notar que uma lista de itens desejados pode revelar uma gravidez, uma religião ou uma condição médica; desenhe os campos para não coletar o que não precisa, e trate texto livre como potencialmente sensível. A pessoa dona do dado detém os direitos; você, que decide por que e como ele é tratado, é o controlador; Supabase e Cloudflare, tratando sob suas instruções, são operadores.

Os princípios do artigo 6 são o briefing de design. Finalidade: colete por um motivo específico e declarado. Adequação e necessidade: só o que esse motivo precisa. Transparência: diga às pessoas, em linguagem clara, o que você faz. Segurança: medidas proporcionais ao risco. Prevenção, não discriminação, responsabilização. O inventário é o primeiro passo prático: uma tabela com todo campo que você guarda, com finalidade, base legal que pretende usar, quem acessa, qual fornecedor o mantém e por quanto tempo. Essa tabela alimenta a política de privacidade, o fluxo de exclusão e o plano de incidentes, e é o que a ANPD, a autoridade nacional, pediria para ver.

Como aplicar

  • Inventarie todo campo com finalidade, base legal, acesso, fornecedor e retenção.
  • Colete menos: se a finalidade não precisa da data de nascimento, não peça.
  • Nomeie os papéis: você é o controlador; liste seus operadores.
  • Trate texto livre como capaz de ser sensível e mantenha privado por padrão.

Detalhes que fazem a diferença

  • Endereços IP e ids de dispositivo são dado pessoal. Logs contam.
  • Pseudonimizado ainda é pessoal; só anonimização de verdade sai da lei.
  • Dados de crianças exigem consentimento específico dos pais e o melhor interesse da criança.
  • O inventário é documento vivo; atualize a cada campo novo.
  • Isto é educação, não assessoria jurídica; uma pessoa advogada revisa antes do lançamento.
Fontes: Lei nº 13.709/2018 (LGPD), texto integral · ANPD, Autoridade Nacional de Proteção de Dados · ANPD, materiais educativos e publicações · Serpro, LGPD explicada

Legal Bases and the Rights of Data Subjects

Consentimento é uma de dez bases legais, e em geral não a melhor. Operar a conta que a pessoa pediu é execução de contrato; prevenir fraude é legítimo interesse. Seja qual for a base, a pessoa mantém direitos: acesso, correção, portabilidade, exclusão, e resposta em prazo razoável.

Por quê

A LGPD lista as bases legais no artigo 7: consentimento, obrigação legal, políticas públicas, pesquisa, execução de contrato, exercício de direitos, proteção da vida, tutela da saúde, legítimo interesse, proteção ao crédito. Um produto que pede consentimento para tudo ganha dois problemas: consentimento pode ser revogado a qualquer momento, o que significaria excluir a conta que a pessoa ainda quer, e um termo longo que ninguém lê não é o consentimento livre, informado e inequívoco que a lei exige. Para a wishlist, guardar o e-mail e as listas é execução do contrato que a pessoa aceitou ao se cadastrar; logs de segurança são legítimo interesse; uma newsletter de marketing é consentimento, separado, opt-in, revogável com um clique.

Direitos são a outra metade. A pessoa pode confirmar se você trata seus dados, acessá-los, corrigi-los, anonimizar ou excluir o desnecessário, recebê-los em formato portável, saber com quem você compartilhou, e revogar consentimento. Cada direito precisa de um caminho no produto ou de um processo manual documentado, e de resposta nos prazos da lei. Construa os óbvios: uma exportação dos dados da pessoa em JSON, exclusão de conta que exclui de verdade, uma página de perfil onde os campos são editáveis, e um canal de contato que responde. Registre pedidos e respostas; responsabilização é princípio, e o registro é sua prova.

Como aplicar

  • Escolha a base por finalidade: contrato para o serviço, legítimo interesse para segurança, consentimento só para extras.
  • Consentimento é granular, opt-in e revogável onde você o usar.
  • Entregue exportação e exclusão como funcionalidades, não como tickets de suporte.
  • Registre pedidos e respostas com datas.

Detalhes que fazem a diferença

  • Caixas pré-marcadas não são consentimento.
  • Legítimo interesse exige um teste de ponderação escrito que você possa mostrar.
  • Exclusão tem exceções: obrigações legais podem exigir guardar alguns registros; diga quais.
  • Portabilidade é exportação legível por máquina, JSON serve.
  • Designe um encarregado mesmo que seja você, e publique o contato.
Fontes: Lei nº 13.709/2018 (LGPD), artigos 7, 11 e 18 · ANPD, materiais educativos e publicações · ICO, Guide to the data protection principles (paralelo com o GDPR)

Privacy by Design in the Product

Privacy by design significa que a escolha segura é o padrão e a escolha privada é real no backend, não um botão que esconde outro. Controles de visibilidade, exclusão, retenção, cookies e a política de privacidade são funcionalidades de produto, construídas com o mesmo cuidado da própria wishlist.

Por quê

A LGPD pede privacidade desde a concepção e por padrão. Na wishlist isso significa: listas novas privadas, campos de perfil mínimos, analytics desligado até a pessoa concordar, e todo "privado" na interface sustentado por uma política no banco e no storage. A política de privacidade e os termos de uso são documentos diferentes com trabalhos diferentes: a política explica quais dados, por quê, em qual base, com quem, por quanto tempo e como exercer direitos; os termos fixam as regras do serviço. Os dois são lidos por poucos e importam a todos; escreva em linguagem simples e mantenha exatos, porque uma política que promete o que o sistema não faz é por si uma violação.

Cookies ganham parágrafo próprio porque o folclore está errado. Cookies estritamente necessários, a sessão e a preferência que você precisa para rodar o serviço, não exigem banner de consentimento. Analytics e marketing exigem uma escolha real, desligada por padrão, com a mesma facilidade para recusar e para aceitar; a ANPD publicou orientação exatamente sobre isso. Retenção fecha o ciclo: decida por quanto tempo guarda uma conta inativa, dados de lista excluída, logs e backups, e automatize a exclusão. Excluir conta precisa cascatear por linhas, arquivos e, dentro da janela de backup, backups também, e a pessoa deve receber confirmação. Por fim, um contato de privacidade que responde, e um histórico datado de mudanças na política.

Como aplicar

  • Privado por padrão, todo controle de visibilidade imposto no banco e no storage.
  • Política de privacidade e termos como páginas separadas, em linguagem simples, fiéis ao que o código faz.
  • Escolha de cookies só para analytics e marketing, desligados por padrão, recusar tão fácil quanto aceitar.
  • Cronograma de retenção automatizado, exclusão cascateando por linhas, arquivos e backups.

Detalhes que fazem a diferença

  • Excluir é excluir: linhas, objetos no storage, índices de busca, e a janela de backup declarada.
  • Sem banner para cookies necessários; o que bloqueia a página para tudo é o anti-padrão.
  • O diálogo de compartilhar é um momento de privacidade: repita o que ficará visível.
  • Versione a política com datas, e avise em mudanças relevantes.
  • Perfil mínimo: handle e nome de exibição; o resto opcional.

Vendors, Incidents and the Pre-Launch Review

Supabase, Cloudflare e GitHub tratam os dados dos seus usuários em seu nome, muitas vezes fora do Brasil. Conheça os termos, saiba onde os dados moram, e tenha um plano para o dia em que algo der errado. Depois rode a revisão de pré-lançamento: três usuários, toda operação, todo arquivo, todo header, com evidência.

Por quê

Operadores fazem parte da sua responsabilidade. Leia os termos de tratamento de dados de cada fornecedor, anote as regiões onde os dados ficam, e registre no inventário; a LGPD regula transferências internacionais e a ANPD tem regras para elas, então um banco numa região fora do Brasil é decisão a documentar, não acidente. Suboperadores mudam: assine os avisos dos fornecedores. Incidentes vão acontecer: uma chave vazada, um erro de política que expôs listas privadas, uma conta comprometida. A LGPD exige comunicar incidentes relevantes à ANPD e às pessoas afetadas; o plano prático tem quatro passos, detectar, conter, avaliar, comunicar, com contatos, modelos e critérios de decisão escritos antes de precisar.

A revisão de pré-lançamento é onde esta seção inteira vira evidência. Percorra a matriz de permissões com visitante, dono e outro usuário, pela API, para toda operação, e registre resultados. Busque imagens privadas por URL como o usuário errado. Revise os fluxos de auth, regras de senha, e-mails e todo redirecionamento. Cheque headers, CSP, HTTPS, limites de upload e tratamento de URLs externas. Confirme que segredos estão fora do repositório e do bundle, dependências atualizadas, backups restauram, alertas disparam. Releia inventário, política, cronograma de retenção e fluxo de exclusão contra o que o código de fato faz. Liste os riscos residuais que aceita e os itens que adia, com responsável e data. Lance com esse documento, não com uma sensação.

Como aplicar

  • Tabela de fornecedores: o que cada um trata, onde, sob quais termos, com link para o feed de avisos.
  • Plano de incidentes numa página: detectar, conter, avaliar, comunicar, com contatos e modelos.
  • Revisão de pré-lançamento com evidência: toda célula da matriz testada, todo check com print ou log anexado.
  • Registro de riscos residuais assinado antes de usuários reais chegarem.

Detalhes que fazem a diferença

  • "Configurado" não é "testado". A revisão testa.
  • Pratique o plano de incidentes com um exercício de mesa de chave vazada.
  • Reteste depois de toda mudança de esquema ou política, automatizado onde der.
  • Prioridade se o tempo for curto: RLS e testes entre usuários, depois auth, depois storage e segredos, depois OWASP, depois documentos da LGPD.
  • Esta trilha é educação; não é certificação nem conformidade jurídica. Peça revisão antes do lançamento.
