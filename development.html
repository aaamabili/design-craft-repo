Section 10

Development

Shipping a real web app with accounts, shared profiles and private data, without leaking any of it. HTTP, authentication, Postgres and Row Level Security, the OWASP failures, secrets and infrastructure, and the LGPD as a product requirement, built around one concrete app: a wishlist.

Development · 01

How the Web Talks

Every screen you design is a sequence of HTTP requests. Method says intent, path says resource, status says what happened. Reading them in the Network tab is the first security skill, because everything else is about who may send which request.

Why

A wishlist app is a browser talking to an API over HTTP. The browser sends a request with a method, a path, headers and sometimes a body; the server answers with a status code, headers and a body, usually JSON. The methods carry meaning: GET reads, POST creates, PATCH changes part of something, DELETE removes. Status codes carry the outcome: 200 ok, 201 created, 204 done with nothing to return, 400 you sent something wrong, 401 you are not identified, 403 you are identified and still not allowed, 404 not here, 429 slow down, 500 we broke. The difference between 401 and 403 is the difference between authentication and authorization, and it shows up in the Network tab long before it shows up in a design.

Headers are where the interesting security material lives. The request carries the token or cookie that identifies the person; the response carries the policies that constrain the browser. Open DevTools on any app you use, filter by Fetch/XHR, and read one request end to end. You will see what the app sends, what it gets back, and how little the pretty interface has to do with what the server actually enforces. One rule for this whole section: never paste a real token or cookie into a screenshot or a chat. Treat them as passwords, because they are.

How to apply

  • Read the Network tab of your own app once a week. Method, path, status, headers, body.
  • Use methods for meaning. A GET never changes data; a DELETE never pretends to be a POST.
  • Map status codes to UI states: 401 goes to login, 403 says "not yours", 404 says "nothing here", 429 asks to wait.
  • Draw the diagram React → Supabase (Auth, PostgREST, Storage) with every arrow labeled by what it carries.

Details that make the difference

  • 401 and 403 are different screens. One asks who you are, the other says no.
  • 204 means success with an empty body; do not show an error because the JSON was empty.
  • Idempotency: GET, PUT and DELETE can be repeated safely; POST cannot.
  • The body of a 4xx is for developers; the UI copy is yours.
  • Tokens in screenshots are leaks. Redact before sharing.
Sources: MDN, An overview of HTTP · MDN, HTTP response status codes · MDN, HTTP request methods
Development · 02

What TLS Protects

HTTPS encrypts the conversation between the browser and the server. It hides the content and the path, verifies you reached the right server, and stops tampering in transit. It does nothing for data at rest, nothing against a malicious page, and nothing about who the server lets in.

Why

Transport Layer Security wraps HTTP so that someone on the same network, the ISP, or a hostile proxy sees only which host you connected to and roughly how much data moved. Headers, cookies, tokens, request bodies and responses are all inside the tunnel. The certificate proves the server is who the domain says it is, which is what defeats a fake "login page" sitting between you and the real one. Cloudflare Pages and Supabase give you this by default, with certificates renewed for you; your job is to never offer a plain-HTTP path and to tell browsers to stop trying one, through HSTS.

The limits matter as much as the guarantees. TLS protects bytes in motion, not bytes stored in the database, in backups, or in a log line. It does not stop a script injected into your page from reading what the page can read. It does not decide whether user B may see user A's private list; that is authorization, inside the tunnel, decided by the server. "The site has the padlock" means exactly one thing: the network between the person and your server is not the weak point.

How to apply

  • HTTPS everywhere, no exceptions, including the API base URL in your config.
  • Enable HSTS on the Pages project so browsers refuse plain HTTP after the first visit.
  • Do not mistake the padlock for safety. It covers transit, not storage, scripts or permissions.
  • Mixed content is a break: an http image or script on an https page weakens the page.

Details that make the difference

  • What the network still sees: the hostname (SNI), timing and sizes.
  • Certificates expire; managed platforms renew them, self-hosted ones need a job.
  • HSTS preload is a commitment; add it only when every subdomain is ready.
  • Local dev over http is fine; production over http is not.
  • TLS is not encryption at rest. Ask what encrypts the database and the backups.
Sources: MDN, Transport Layer Security · web.dev, Why HTTPS matters · MDN, Strict-Transport-Security · OWASP, TLS cheat sheet
Development · 03

Cookies, Sessions and Browser Storage

The browser keeps state in three places: cookies, which travel with requests; localStorage and sessionStorage, which scripts read; and memory, which vanishes on reload. Where the session token lives decides which attacks can steal it.

Why

A session is the server remembering who you are between requests. The usual carrier is a token, and the token has to be stored somewhere in the browser. Cookies are sent automatically with every request to their domain, which is convenient and also the root of CSRF; with the HttpOnly flag a script cannot read them, which is the best defense against XSS stealing them; with Secure they only travel over HTTPS; with SameSite they stop being attached to cross-site requests. localStorage is the opposite trade: nothing is sent automatically, so CSRF is moot, but any script running on the page can read it, so one XSS hole hands over every session.

Supabase's browser client stores the session in localStorage by default; server-side rendering setups move it to cookies. Either choice is defensible once you know what it costs: with localStorage, XSS is the whole game and the Content Security Policy becomes mandatory; with cookies, SameSite and CSRF protections become mandatory. What is never defensible is a token in a URL, a token in a log, or a token that never expires. Headers are the third storage you do not control: the Authorization header is how a token reaches the API on each call, and the Network tab shows it in clear text to anyone with the laptop open.

How to apply

  • Know where your session lives and write the matching defenses: CSP for localStorage, SameSite and CSRF tokens for cookies.
  • Cookies get HttpOnly, Secure and SameSite by default, every time.
  • Nothing sensitive in sessionStorage either; it is script-readable too, just shorter-lived.
  • Never put a token in a URL. URLs end up in logs, history and referrers.

Details that make the difference

  • HttpOnly is for the token, not for preferences. Theme can live in localStorage.
  • SameSite=Lax is the sensible default; Strict breaks links from email, None needs Secure.
  • Logout must clear the storage, not only the UI state.
  • Shared computers: a persisted session is a decision, offer "keep me signed in" explicitly.
  • Inspect Application → Storage in DevTools to see exactly what your app leaves behind.
Sources: MDN, Using HTTP cookies · OWASP, Session management cheat sheet · OWASP, HTML5 security cheat sheet (local storage) · Supabase, Sessions
Development · 04

Same-Origin Policy and CORS

The browser stops a page on one origin from reading responses from another. CORS is the server saying which origins may. It protects users from malicious pages; it does not protect your API from anyone with curl.

Why

An origin is scheme plus host plus port. The same-origin policy says a script on evil.example cannot read the response of a request to your API, even if the browser sent it. That is a user protection: it keeps a random page from pulling your logged-in data through the user's own browser. CORS loosens it on purpose: the API answers with Access-Control-Allow-Origin naming the origins that may read, and for non-simple requests the browser first sends a preflight OPTIONS to ask. Supabase allows your project to be called from any origin because the real gate is the token and Row Level Security, not the origin.

The misunderstanding to kill early: CORS is enforced by browsers, for browsers. A script, a mobile app, Postman or curl ignores it entirely. If your API only works because "the frontend is the only thing calling it", it is open. Likewise a wildcard Allow-Origin with credentials is a misconfiguration the browser will refuse, and a reflected Allow-Origin (echoing whatever origin asked) is an open door for the attacks the policy exists to prevent. The rule for the wishlist: assume every endpoint will be called directly, by anyone, and make the database say no.

How to apply

  • Treat CORS as a browser courtesy, never as access control.
  • Allow specific origins, never reflect the request origin, never wildcard with credentials.
  • Every endpoint must be safe to call with curl and a stolen or absent token.
  • Read the preflight in the Network tab once, so OPTIONS stops being mysterious.

Details that make the difference

  • Scheme, host, port: https://app and http://app are different origins.
  • Site vs origin: SameSite cookies use the site; CORS uses the origin.
  • Preflight caches; a failing OPTIONS shows up as a vague "network error" in the console.
  • Supabase is origin-agnostic by design; RLS is the gate.
  • If removing the frontend would expose data, the backend was never protected.
Sources: MDN, Same-origin policy · MDN, Cross-Origin Resource Sharing · PortSwigger, CORS · web.dev, Same-site and same-origin
Development · 05

Authentication vs Authorization

Authentication answers who you are. Authorization answers what you may do. Most real breaches are authorization failures: the system knew exactly who the person was and still handed them someone else's data.

Why

Logging in proves identity: this request comes from the account that knows the password, holds the magic link, or passed the second factor. It says nothing about permissions. Authorization is the separate decision, made on every request, that this identity may read this list, edit this item, delete this account. The two are confused constantly because the login screen is visible and the permission check is not. OWASP has put Broken Access Control at the top of its list since 2021 precisely because teams build beautiful login flows and then trust the frontend to hide the buttons users should not press.

For the wishlist, the authorization model is small and must be written down: a visitor can read public lists; a logged-in person can read public lists and everything they own; nobody but the owner can write. That matrix is the specification. It gets enforced in the database, through Row Level Security, so that every path to the data, the app, a direct API call, a future mobile client, obeys the same rules. Hiding an Edit button is interface; denying the UPDATE is security. Both are needed, in that order of importance reversed.

How to apply

  • Write the permission matrix before writing a table: operation × role, with Yes or No in each cell.
  • Enforce in the database, reflect in the UI. Never the other way around.
  • Authorize on every request, not once at login.
  • Test as three people: a visitor, the owner, another user, for every operation.

Details that make the difference

  • "Logged in" is not a permission. It is an identity.
  • Default deny: everything is forbidden until a rule allows it.
  • Owner is a column, not a feeling: user_id on every row that belongs to someone.
  • Admin is a role with its own audit, not a shared password.
  • The matrix is the test plan. Each cell is one test.
Sources: Auth0, Authentication vs. authorization · OWASP, Authorization cheat sheet · OWASP Top 10, A01 Broken Access Control
Development · 06

Sign Up, Sign In, Recover

Account flows are where security and UX meet hardest. Email verification, password rules, recovery links and logout each have a correct shape, and Supabase Auth implements most of it, but the product still has to decide what is required and what the person sees.

Why

Sign-up creates an identity; sign-in proves it; logout ends the session; recovery lets someone back in without the password. Each step is an attack surface. Unverified emails let people register addresses they do not own, which later become a way to hijack accounts or spam. Weak password rules invite credential stuffing; the fix is a minimum length, a check against breached passwords, and no composition rules that produce "Password1!". Recovery is the classic hole: a link that never expires, that works more than once, or that reveals whether an email exists, hands accounts to attackers. Logout that only clears the UI leaves a valid token on the device.

Supabase Auth gives you sign-up with confirmation emails, password sign-in, magic links, OAuth providers, password recovery and session handling. The decisions left to you are product decisions: require verification before any write; show the same neutral message whether or not the email exists; expire recovery links fast and once; invalidate other sessions on password change; and make "Sign out" revoke the refresh token, not only drop the local state. Document the flow as a diagram with every state, including the sad ones, because that diagram is also the UX spec.

How to apply

  • Require email verification before the account can create or share anything.
  • Neutral messages: "If that email exists, we sent a link", for sign-up, recovery and login errors alike.
  • Recovery links expire and are single-use; password change invalidates other sessions.
  • Sign out revokes the session server-side and clears local storage.

Details that make the difference

  • Minimum 12 characters, no composition rules, check against known breaches.
  • The verification email is part of the product: write it, test it, brand it.
  • Custom SMTP in production; the default sender has strict limits.
  • Redirect targets are allowlisted, never taken from a query string.
  • Two test accounts, always. One is never enough to find an authorization bug.
Sources: Supabase, Auth overview · Supabase, Password-based auth · Supabase, Password security · OWASP, Forgot password cheat sheet · OWASP, Authentication cheat sheet
Development · 07

Tokens, JWTs and Expiry

A JWT is a signed statement about who the holder is, valid until it expires. Short-lived access tokens limit the damage of theft; refresh tokens extend the session without a new login. Signed is not encrypted: anyone can read a JWT.

Why

After login, Supabase issues an access token, a JSON Web Token signed by the project, and a refresh token. The access token travels with every API call in the Authorization header; Postgres reads its claims, which is how auth.uid() knows who is asking. It expires in about an hour by default. When it does, the client uses the refresh token to get a new pair, silently. The design is a trade: short access tokens mean a stolen one is useful briefly; refresh tokens mean the person does not log in every hour. Refresh token rotation, on by default, makes each refresh token single-use, so a stolen one that is replayed after the legitimate client used it gets the whole session revoked.

Three facts prevent most JWT mistakes. One: the payload is base64, not encrypted, so never put secrets in it and assume the person can read their own claims. Two: the server does not look the token up; it verifies the signature, which is why revocation is hard and expiry is the real control. Three: the signing secret and the service role key are the keys to the kingdom; they never leave the server. Session expiry is also a product decision: a wishlist does not need bank-grade timeouts, but "remember me forever" on a shared computer is a choice to make consciously, with a visible way to sign out everywhere.

How to apply

  • Keep access tokens short, let the client refresh silently, keep rotation on.
  • Never trust client-side claims for permissions; the database verifies the signature and applies RLS.
  • Offer "sign out of all devices" and trigger it on password change.
  • Decode a token once in jwt.io with a test account, so you know exactly what it carries.

Details that make the difference

  • exp is the control. Everything else about a JWT is convenience.
  • Rotation detects reuse: a replayed refresh token kills the session.
  • The role claim is "authenticated" or "anon", not your app's admin flag.
  • Clock skew exists; do not panic over a token rejected a few seconds early.
  • Tokens in logs are credentials in logs. Scrub the Authorization header.
Sources: Supabase, JSON Web Tokens · Supabase, User sessions · jwt.io, Introduction to JSON Web Tokens · PortSwigger, JWT attacks
Development · 08

Rate Limits, CAPTCHA, MFA and Redirects

Attackers automate. Rate limits make guessing expensive, CAPTCHA raises the cost of bots where it is worth the friction, MFA protects the accounts that matter most, and a redirect allowlist keeps your login from becoming a phishing launcher.

Why

A login form without limits is an oracle: try a million passwords, keep the ones that work. Supabase applies rate limits on auth endpoints and lets you tune them; your app should also back off on the client, show the 429 as "too many attempts, wait a minute", and never reveal whether the email or the password was the wrong half. CAPTCHA, through providers like Cloudflare Turnstile, belongs on sign-up and recovery, where bots create junk accounts and trigger email floods, and should stay off the daily login path unless abuse appears, because every challenge is friction paid by honest people.

Multi-factor authentication is the single biggest upgrade for the accounts that can do damage: yours, as the admin, and any role with elevated rights. Supabase supports TOTP; requiring it for admin logins costs seconds and removes the password as a single point of failure. Redirects are the quiet one: auth flows send people back to a URL after login or recovery, and if that URL comes from the request, a crafted link logs someone in on your real site and lands them on an attacker's page. Supabase only redirects to URLs you register; keep that list tight and never append to it from user input.

How to apply

  • Rate limits on auth and on any endpoint that sends email; show 429 as a calm "wait".
  • CAPTCHA on sign-up and recovery, not on every login, unless you see abuse.
  • MFA required for admin accounts, optional for everyone else, with recovery codes.
  • Redirect allowlist only. No open redirects, no redirect from query strings.

Details that make the difference

  • Same error for wrong email and wrong password. Enumeration starts with a helpful message.
  • Lockouts are a denial-of-service vector; prefer backoff over hard locks.
  • Turnstile over image puzzles: invisible for most people, costly for bots.
  • Admin is a separate login story, with MFA and its own audit log.
  • Test a crafted redirect once to see the allowlist refuse it.
Sources: Supabase, Rate limits · Supabase, Bot detection with CAPTCHA · Supabase, Multi-factor authentication · Supabase, Redirect URLs · OWASP, Unvalidated redirects cheat sheet · Cloudflare Turnstile
Development · 09

Modeling Profiles, Lists and Items

Three tables carry the wishlist: profiles, wishlists, wishlist_items. Foreign keys make the relations real, constraints make bad data impossible, and the owner column on every row is what Row Level Security will later check. Model for the permissions you will need.

Why

Supabase keeps authentication in auth.users, which you do not edit directly. The public profile (display name, handle, avatar) lives in a profiles table keyed by the same id, created by a trigger when a user signs up. Wishlists reference the profile through a user_id foreign key and carry a visibility column; items reference their wishlist. Foreign keys with ON DELETE CASCADE mean deleting an account removes its lists and items, which is both tidy and, as you will see in the LGPD lessons, a legal need. Constraints do the rest of the hygiene: NOT NULL where a value is required, UNIQUE on the handle, CHECK on visibility so only the three allowed values exist, and a length limit on titles so nobody stores a novel.

Indexes make the common queries fast: wishlists by user_id, items by wishlist_id, profiles by handle. Primary keys as UUIDs instead of sequential integers close the cheapest attack there is, guessing the next id, though UUIDs are not a substitute for authorization. Write the schema as SQL migrations in the repository, not as clicks in a dashboard; versioned SQL is what lets you rebuild the database, review a change, and know which policy existed when.

How to apply

  • profiles(id → auth.users), wishlists(user_id, visibility), wishlist_items(wishlist_id). Owner column on everything owned.
  • Constraints before code: NOT NULL, UNIQUE, CHECK, length limits.
  • UUID primary keys, and indexes on every foreign key you filter by.
  • Migrations in git. The dashboard is for reading, the repository is for truth.

Details that make the difference

  • Never store the email in profiles unless you need it public; auth.users already has it.
  • CASCADE deletes are a design decision; write down what disappears with an account.
  • Timestamps with time zone, created_at and updated_at on every table.
  • Visibility as a CHECK constraint, not a free string.
  • Seed with fictional data and keep a script to reset it.
Sources: Supabase, Managing user data · PostgreSQL, Constraints · PostgreSQL, Indexes · Supabase, Cascade deletes · PostgreSQL, Tutorial
Development · 10

Row Level Security

RLS turns authorization into database rules: each table gets policies that say which rows a given user may select, insert, update or delete. With auth.uid() in the policy, the database itself refuses what the person may not do, whoever is asking and from wherever.

Why

Supabase exposes your tables through an API that the browser calls directly with the person's token. That only works because Row Level Security is on: a table without RLS and with the anon key in the client is public to the world. With RLS enabled, Postgres evaluates a policy for every row on every operation. The policy can read auth.uid(), the id from the verified token, and compare it with the owner column. One policy per operation keeps the logic readable: SELECT allows owners and, for public lists, everyone; INSERT checks that the new row's user_id is the caller; UPDATE and DELETE allow only the owner. Policies are additive: if any policy permits, the row passes, so a permissive leftover from testing is a hole.

Two practices keep RLS honest. First, test it from outside the UI: run the same query as a visitor with no token, as user A, as user B, through the API, and compare the rows. Second, keep the policies in migrations and review them like code, because a policy is code. Performance follows: wrap auth.uid() in a subselect so it is evaluated once, index the columns policies compare, and avoid joins inside policies. Supabase's advisors flag tables without RLS and policies that look wrong; run them before every release.

How to apply

  • ALTER TABLE … ENABLE ROW LEVEL SECURITY on every table, before the first row.
  • One policy per operation, named for what it allows: "owners update their wishlists".
  • INSERT uses WITH CHECK so nobody creates rows owned by someone else.
  • Test from the API as three people and keep the results as a table in the repo.

Details that make the difference

  • No RLS plus anon key equals public table. There is no middle state.
  • Policies are OR-ed. Delete the "allow all for testing" one.
  • (select auth.uid()) instead of auth.uid() for speed on big tables.
  • service_role bypasses RLS, which is why it never reaches the client.
  • Views and functions need their own thought; security definer functions skip RLS.
Sources: Supabase, Row Level Security · PostgreSQL, Row security policies · PostgreSQL, CREATE POLICY · Supabase, Securing your data · Supabase, Database advisors
Development · 11

Public, Unlisted, Private

A wishlist has three audiences: anyone, anyone with the link, only the owner. Each tier is a policy in the database and a sentence in the interface. If the sentence promises more than the policy enforces, the product is lying.

Why

Public lists appear in search and on the profile; unlisted lists open for anyone who has the URL but are not listed anywhere; private lists are the owner's alone. The difference is trivial in the UI and decisive in the database. Public: SELECT allowed for everyone where visibility = public. Unlisted: SELECT allowed for everyone by id, but the list query that feeds the profile page excludes them, so discovery depends on knowing the UUID, which is why the id must be unguessable. Private: SELECT only for the owner. Items inherit the list's visibility through a policy that joins to the parent, or through a denormalized column kept in sync by a trigger.

The interface has to say exactly what each tier means, where the person chooses it, in plain words: "Anyone can find this list", "Only people with the link", "Only you". The LGPD's transparency principle makes this more than good manners. And the default matters: a new list should be private until the person decides otherwise, because an accidental public list is a data leak the person did not consent to. Test the tiers the way an attacker would: fetch an unlisted list by id without a token, list a profile's lists and check that unlisted ones are absent, fetch a private list as another user and expect nothing back.

How to apply

  • Three values, one CHECK constraint, three policies. No other states.
  • Private by default. Sharing is an action the person takes.
  • Plain-language labels at the control, not in a help page.
  • Items follow the list; never let an item be more visible than its parent.

Details that make the difference

  • Unlisted means unguessable: UUID v4 ids, no sequential numbers anywhere.
  • Changing to private must take effect immediately, including cached pages and images.
  • Search indexes only public lists; unlisted must never leak via search.
  • The share dialog repeats the visibility at the moment of copying the link.
  • Image URLs follow the tier too; a private list with public image URLs is not private.
Sources: Supabase, Row Level Security · OWASP, Authorization cheat sheet · ANPD, materiais educativos
Development · 12

Broken Access Control and IDOR

Change the id in the URL and see someone else's data: that is an Insecure Direct Object Reference, the most common serious bug on the web. The fix is never to hide the id; it is to make every query check ownership, which RLS does if the policies are right.

Why

OWASP ranks Broken Access Control first because it is everywhere and it is simple: the app checks who you are, fetches the record you asked for, and forgets to check whether the record is yours. The API version is called BOLA, Broken Object Level Authorization. Symptoms: changing /lists/42 to /lists/43 shows another person's private list; a PATCH to someone else's item succeeds; an export endpoint returns everyone's data because the filter was applied in the frontend. Unguessable ids slow this down and do not fix it; an attacker who ever sees an id, in a shared link or a screenshot, has it forever.

The defense is structural. With RLS enabled and correct, the query that fetches list 43 returns nothing for the wrong user, whatever the frontend sent. The remaining work is testing: for every operation in the permission matrix, perform it as the wrong user through the API and confirm the refusal. Keep a document of these tests with the request, the expected result, and the actual result; it is the evidence your access control works, and the first thing to rerun after any schema change. Also watch the second-order paths: joins that pull related rows, functions that run with elevated rights, and storage files whose URLs skip the database entirely.

How to apply

  • Every object fetch is filtered by ownership or visibility, in the database.
  • Test id swapping on every endpoint, as a visitor and as another user.
  • Unguessable ids are a courtesy, not a control.
  • Keep the offensive test log next to the schema and rerun it on change.

Details that make the difference

  • Deny by default returns empty or 404, not 403 with the object's name.
  • Mass assignment is the cousin: never let the client set user_id or visibility on another's row.
  • Bulk endpoints filter per row, not per request.
  • Functions with SECURITY DEFINER need their own ownership checks.
  • Automate the three-user test once it works by hand.
Sources: OWASP Top 10, A01 Broken Access Control · PortSwigger, Access control vulnerabilities · PortSwigger, IDOR · OWASP API Security, Broken Object Level Authorization
Development · 13

XSS and Safe Rendering

Cross-site scripting is user content executing as code in another user's browser. The defense is to render text as text: React does it by default, dangerouslySetInnerHTML undoes it, and a Content Security Policy catches what slips through.

Why

A wishlist stores text people type: item names, notes, profile bios, URLs. If any of it is inserted into the page as HTML, a note containing a script tag runs in the browser of everyone who views the list, with their session. That is stored XSS, and with the session in localStorage it is game over for every viewer. React escapes text in JSX, so the ordinary path is safe; the holes are the escape hatches: dangerouslySetInnerHTML, writing to innerHTML, building HTML strings, and attributes that take URLs, where javascript: links execute on click. Markdown rendering is a classic source, because the renderer produces HTML from untrusted text.

The rules are short. Never render user content as HTML unless it has passed a sanitizer like DOMPurify with an allowlist of tags. Validate URLs before using them as href or src: only http and https, nothing else. Set a Content Security Policy that forbids inline scripts, so even an injected tag does not run. And test with the payloads that matter: a script tag, an img with onerror, a javascript: URL, an svg with onload, in every field that is later displayed. Output encoding is contextual, which is why "escape everything" is not a strategy; the context (HTML text, attribute, URL, JavaScript) decides the encoding.

How to apply

  • Text stays text. No dangerouslySetInnerHTML with user content, ever.
  • Sanitize with an allowlist if you must render rich text; DOMPurify, not a regex.
  • Allow only http(s) in URLs people enter; render the rest as plain text.
  • CSP without unsafe-inline as the second layer.

Details that make the difference

  • Markdown is HTML with extra steps; sanitize after rendering.
  • Test fields with <img src=x onerror=alert(1)> and a javascript: link.
  • DOM XSS lives in the client: location.hash into innerHTML is a classic.
  • rel="noopener" on links to user-provided URLs.
  • Third-party scripts share your origin; load as few as possible.
Sources: PortSwigger, Cross-site scripting · OWASP, XSS prevention cheat sheet · OWASP, DOM-based XSS prevention · React, dangerouslySetInnerHTML · DOMPurify
Development · 14

SQL Injection

Injection happens when data is glued into a query as text and the database reads it as code. Parameterized queries keep the two apart. Supabase's client and PostgREST parameterize for you; the risk returns the moment you build SQL strings yourself.

Why

The attack is forty years old and still on the OWASP list because string concatenation is easy. A search box that becomes WHERE title = '… turns a single quote into a way to end the string and write more SQL: read other tables, bypass a login, drop a table. The defense is not escaping quotes; it is never mixing data into the query text. Parameterized queries send the SQL and the values separately, so the database treats the value as a value, whatever characters it holds. Supabase's JavaScript client builds parameterized requests, and PostgREST does the same on the server, so the ordinary path is safe.

The holes appear where you write SQL: database functions that build dynamic queries with string concatenation, RPC calls that take raw fragments, Edge Functions that talk to Postgres directly, and admin scripts. In Postgres functions use format() with %L and %I, or EXECUTE … USING, never || with user input. Input validation helps for sanity (a page number is a number) but is not the defense; a valid-looking string can still be an injection. Test with the classic payloads in every input that reaches a query and watch for errors that leak the query, which is itself information disclosure.

How to apply

  • Parameters, never concatenation, in every place that touches SQL.
  • In Postgres functions, format() with %L/%I or EXECUTE … USING.
  • Database user with least privilege for any server-side code you write.
  • Error messages for users are generic; the real error goes to the log.

Details that make the difference

  • Test with ' OR 1=1 -- and a quote in every field.
  • ORMs and clients are safe until you call .raw() or build a filter string.
  • Column and table names are not parameters; allowlist them.
  • Full-text search inputs still go through parameters.
  • A leaked error with SQL in it is a finding on its own.

CSRF and When It Applies

Cross-site request forgery is another site making the browser send a request to yours with the user's cookies attached. It only works when the credential travels automatically. Know which model you use, then apply the matching defense.

Why

Cookies are attached to requests by the browser, regardless of which page started them. A hidden form on evil.example that posts to your API would arrive carrying the victim's session cookie, and the server would believe it. That is CSRF. The defenses are SameSite cookies, which stop the browser from attaching cookies to cross-site requests, anti-CSRF tokens the attacker cannot know, and checking the Origin header. If instead the session token lives in localStorage and is sent as an Authorization header by your own JavaScript, a foreign page cannot add that header, and CSRF does not apply; the price, as the storage lesson said, is that XSS becomes the whole game.

Supabase's default browser client uses the header model, so a plain wishlist built on it is not CSRF-exposed. The moment you move the session to cookies, for server-side rendering or for a custom backend, CSRF comes back and SameSite=Lax plus origin checks become mandatory. Also remember the non-cookie variants: a logged-in action triggered by a GET (an "unsubscribe" or "delete" link) is forgeable from an image tag, which is one more reason a GET never changes state. Decide the model, write it down, and test it: a form on another origin that posts to your API should fail.

How to apply

  • Header-carried tokens: no CSRF, mandatory CSP. Cookie-carried: SameSite plus tokens or origin checks.
  • State-changing requests are never GET.
  • Check Origin or Referer on the server when cookies are the credential.
  • Test from a foreign page once; expect the request to be refused.

Details that make the difference

  • SameSite=Lax still sends cookies on top-level GET navigation; that is why GET must be safe.
  • CORS does not prevent CSRF; the request is sent, only the response is hidden.
  • Login CSRF exists too: logging the victim into the attacker's account.
  • Double-submit cookies are the simplest token scheme for a small app.
  • Document the session model so the next person applies the right defense.
Sources: PortSwigger, CSRF · OWASP, CSRF prevention cheat sheet · MDN, SameSite cookies · web.dev, SameSite cookies explained

Keys and Secrets

The anon key is designed to be public and useless without RLS. The service role key bypasses RLS and must never leave a server. Environment variables, .gitignore and secret scanning keep the second one out of the bundle and the repository.

Why

Supabase gives every project two kinds of keys. The publishable or anon key identifies the project and ships in the browser; its only power is to call the API as an anonymous or authenticated user, which RLS then constrains. The secret or service role key is the master key: it bypasses every policy and reads and writes anything. It belongs in a server environment, an Edge Function, or a trusted script, never in frontend code, never in a Vite variable prefixed VITE_, because everything with that prefix is compiled into the public bundle. One service role key in a JavaScript bundle equals a public database.

Secrets reach the repository through carelessness: a .env committed by accident, a key pasted in a config file, a screenshot in the docs. The defenses are routine: .env in .gitignore from the first commit, an .env.example with placeholders, GitHub secret scanning turned on, a local scanner like gitleaks in a pre-commit hook, and rotation the moment a key is suspected to have leaked, because git history remembers everything. Cloudflare Pages keeps production variables in its dashboard, separate from preview environments, which is where the dev/prod split starts to matter.

How to apply

  • Anon key in the client, service role key never. No VITE_ prefix on anything secret.
  • .env ignored, .env.example committed, variables set in the hosting dashboard.
  • Secret scanning on the repo and a pre-commit scanner locally.
  • Rotate on suspicion, not on proof. A leaked key is leaked forever in history.

Details that make the difference

  • Search the built bundle for "service_role" before every deploy. It takes ten seconds.
  • Different keys per environment; a leaked staging key must not open production.
  • Rotation is a drill: practice it before you need it.
  • Screenshots of the dashboard often contain keys. Crop.
  • The anon key is public by design; stop treating it as a secret and start treating RLS as the lock.
Sources: Supabase, API keys · Vite, Env variables and modes · GitHub, About secret scanning · OWASP, Secrets management cheat sheet · gitleaks

Storage, Uploads and Signed URLs

Images of gifts are files, and files have their own permissions. Buckets are public or private, policies decide who uploads and who reads, signed URLs give temporary access to private files, and limits on size and type keep uploads from becoming an attack.

Why

Supabase Storage keeps files in buckets with RLS-style policies on the objects table. A public bucket serves any file by URL, forever, to anyone; that is right for avatars and wrong for images in a private list. A private bucket serves files only through authenticated requests or signed URLs, links that expire after a set time. The wishlist needs both: public bucket for profile pictures, private bucket for item images, with policies that mirror the list's visibility, so that a private list's images do not leak through a URL copied once. Path conventions help: user_id/list_id/file, with policies that compare the first folder to auth.uid().

Uploads are input. Limit size per file and per bucket, restrict MIME types to the images you actually display, and never trust the extension; the server decides the content type. Rename files on upload so paths are not user-controlled, which closes path traversal and overwrite tricks. Strip EXIF metadata if location data could leak. And consider what happens on delete: removing an item should remove its image, or you keep paying for, and potentially serving, files that should be gone, which the LGPD will care about.

How to apply

  • Public bucket for avatars, private bucket for list images, policies mirroring list visibility.
  • Signed URLs with short expiry for anything private; never a permanent link.
  • Size and MIME limits at the bucket, server-generated file names, no user paths.
  • Delete files with their rows, and test that a deleted image stops serving.

Details that make the difference

  • Public bucket URLs are cacheable forever; moving a list to private does not recall them.
  • Folder-per-user paths make ownership policies a one-liner.
  • Image transforms on the server also strip dangerous content.
  • SVG uploads can carry scripts; treat them as code, not images.
  • Test the three users on files too, not only on rows.
Sources: Supabase, Storage access control · Supabase, File limits · Supabase, Serving downloads and signed URLs · OWASP, File upload cheat sheet · PortSwigger, File upload vulnerabilities

Security Headers and CSP

A handful of response headers tell the browser how to protect your page: which scripts may run, whether it may be framed, how referrers leak, which features are allowed. Content Security Policy is the heaviest and the most valuable, because it blunts XSS even when a hole exists.

Why

The browser will do a lot for you if asked. Content-Security-Policy lists where scripts, styles, images and connections may come from; a strict policy with no unsafe-inline means an injected script tag simply does not run. Strict-Transport-Security pins HTTPS. X-Content-Type-Options stops MIME sniffing. X-Frame-Options or frame-ancestors prevents your login from being framed into a clickjacking page. Referrer-Policy keeps full URLs, which may include ids of unlisted lists, from leaking to other sites. Permissions-Policy disables camera, geolocation and friends you do not use. Cloudflare Pages sets these through a _headers file in the build output.

CSP is the one that takes work, because a Vite app with a Supabase client, Google Fonts and an analytics script has real sources to declare, and inline styles from libraries fight a strict style-src. Start in report-only mode, read the violations, tighten, then enforce. The connect-src must include your Supabase URL; img-src must include the storage domain; script-src should be your origin plus hashes or nonces, nothing inline. Test with securityheaders.com and with the console open. The reward is that the XSS lesson's worst case, a script in a note, becomes a blocked request instead of a stolen session.

How to apply

  • _headers file on Pages with HSTS, nosniff, frame-ancestors, Referrer-Policy, Permissions-Policy.
  • CSP in report-only first, then enforced, with no unsafe-inline for scripts.
  • Declare only what you use: your origin, Supabase, fonts.
  • Re-check headers after every infra change with an external scanner.

Details that make the difference

  • Referrer-Policy: strict-origin-when-cross-origin keeps unlisted ids out of other sites' logs.
  • frame-ancestors 'none' unless you embed on purpose.
  • Nonces or hashes for the one inline script you cannot avoid.
  • Report-only is not protection; set a date to enforce.
  • Headers are per response; check the API and the storage domain too, not only the page.
Sources: MDN, Content Security Policy · web.dev, Strict CSP · OWASP, HTTP headers cheat sheet · Cloudflare Pages, Headers · securityheaders.com

Dependencies and the Supply Chain

Your app is mostly other people's code. A vulnerable package ships your vulnerability; a hijacked package ships someone's malware. Lockfiles, audits, automated updates and a habit of reading what you install are the controls.

Why

A Vite and React project pulls hundreds of packages, each a potential hole and each a potential path for a malicious update. OWASP lists vulnerable and outdated components in the Top 10; the supply-chain incidents of recent years added typosquatting and maintainer-account takeovers to the list. The baseline is mechanical: commit the lockfile so installs are reproducible, run npm audit in CI and read it, enable Dependabot or an equivalent so updates arrive as reviewable pull requests, and pin major versions of anything that touches auth or rendering. The judgment part is reading: before adding a package, check its maintenance, its download count, its dependency tree and whether you need it at all.

Frontend code runs in the user's browser with the user's session, so a compromised UI library is as dangerous as a compromised backend. Keep the dependency list short, prefer platform features over packages for small needs, and avoid packages that pull in dozens of others for one function. Scheduled, boring updates beat heroic ones: a monthly update window where everything moves a little is safer than a yearly jump that breaks the build. When a vulnerability drops in something you use, know within a day, not a quarter.

How to apply

  • Lockfile committed, npm audit in CI, failures triaged the same week.
  • Automated update PRs with a regular merge cadence.
  • Read before you install: maintainers, activity, size, transitive deps.
  • Fewer packages: every dependency is a standing decision to trust a stranger.

Details that make the difference

  • npm audit fix --force can break things; read the diff.
  • Dev dependencies run on your machine; postinstall scripts are a vector too.
  • Pin by lockfile, not by exact versions in package.json, so patches still flow.
  • Subscribe to advisories for the five packages that matter most.
  • Remove what you stopped using; unused packages still get installed and still get hacked.
Sources: OWASP Top 10, A06 Vulnerable and Outdated Components · npm, npm audit · GitHub, Dependabot · OWASP, Vulnerable dependency management cheat sheet

Logs, Backups and Environments

You cannot defend what you cannot see or restore. Logs tell you something happened, alerts tell you now, backups let you undo it, and a restore test proves the backup is real. Separate environments keep experiments away from real people's data.

Why

Security logging and monitoring failures are an OWASP category of their own because breaches go unnoticed for months. For a small app the bar is modest and still real: Supabase keeps auth, API and database logs; read them when something is odd, and set alerts for the events that matter, failed logins in bursts, errors spiking, unusual volumes of reads. Log what happened and who did it, never what they typed in a password field or the token they carried. Logs are also personal data under the LGPD, so they get a retention period like everything else.

Backups are the difference between an incident and a catastrophe. Supabase takes daily backups on paid plans, with point-in-time recovery available; the free tier does not, which is a reason to decide early what losing everything would mean. A backup nobody has restored is a hope, not a control; schedule a restore into a scratch project and time it. Environments complete the picture: develop against a separate project with fictional data, use preview deployments for review, and keep production keys in production only. Supabase branching and Cloudflare preview deployments make the split cheap; the discipline is never pointing a dev build at the production database "just for a minute".

How to apply

  • Read the logs weekly, alert on failed-login bursts and error spikes.
  • Backups on, restore tested at least once before launch and after big changes.
  • Separate projects for dev and prod, fictional data in dev, previews for review.
  • Logs have retention, and never contain passwords or tokens.

Details that make the difference

  • Timebox the restore drill and write down how long it took.
  • Alert fatigue is a failure mode; three alerts that matter beat thirty.
  • Scrub Authorization headers and emails from anything you ship to a third-party logger.
  • Who has production access? Write the list; keep it short.
  • Migrations run in dev first, then preview, then prod, with a rollback plan.

Personal Data Under the LGPD

Brazil's Lei Geral de Proteção de Dados applies the moment you store a name or an email. It defines personal and sensitive data, names the roles of controller and operator, and sets principles that read like product requirements: purpose, necessity, transparency, security.

Why

Personal data is anything that identifies or can identify a natural person: name, email, handle, photo, IP address, device id, and the combination of innocuous fields that together point at someone. Sensitive data is a narrower set with stricter rules: health, sexual orientation, religion, ethnicity, politics, biometrics, genetics. A wishlist looks harmless until you notice that a list of desired items can reveal a pregnancy, a religion or a medical condition; design the fields so you do not collect what you do not need, and treat free text as potentially sensitive. The person whose data it is holds the rights; you, deciding why and how it is processed, are the controller; Supabase and Cloudflare, processing on your instructions, are operators.

The principles in article 6 are the design brief. Purpose: collect for a specific, stated reason. Adequacy and necessity: only what that reason needs. Transparency: tell people, in clear language, what you do. Security: measures proportional to the risk. Prevention, non-discrimination, accountability. The inventory is the practical first step: a table of every field you store, with its purpose, the legal basis you intend to rely on, who can access it, which vendor holds it and for how long. That table drives the privacy policy, the deletion flow and the incident plan, and it is what the ANPD, the national authority, would ask to see.

How to apply

  • Inventory every field with purpose, legal basis, access, vendor and retention.
  • Collect less: if the purpose does not need the birthday, do not ask.
  • Name the roles: you are the controller; list your operators.
  • Treat free text as sensitive-capable and keep it private by default.

Details that make the difference

  • IP addresses and device ids are personal data. Logs count.
  • Pseudonymized is still personal; only true anonymization leaves the law.
  • Children's data needs specific parental consent and the best interest of the child.
  • The inventory is a living document; update it with every new field.
  • This is education, not legal advice; a lawyer reviews before launch.
Sources: Lei nº 13.709/2018 (LGPD), texto integral · ANPD, Autoridade Nacional de Proteção de Dados · ANPD, materiais educativos e publicações · Serpro, LGPD explicada

Legal Bases and the Rights of Data Subjects

Consent is one of ten legal bases, and usually not the best one. Running the account a person asked for is contract performance; preventing fraud is legitimate interest. Whatever the basis, the person keeps rights: access, correction, portability, deletion, and an answer within a reasonable time.

Why

The LGPD lists the legal bases in article 7: consent, legal obligation, public policy, research, contract execution, exercise of rights, protection of life, health protection, legitimate interest, credit protection. A product that asks for consent for everything gets two problems: consent can be withdrawn at any time, which would mean deleting the account the person still wants, and a long consent form nobody reads is not the free, informed, unambiguous consent the law requires. For the wishlist, storing the email and the lists is execution of the contract the person signed up for; security logs are legitimate interest; a marketing newsletter is consent, separate, opt-in, revocable with one click.

Rights are the other half. The person may confirm whether you process their data, access it, correct it, anonymize or delete what is unnecessary, receive it in a portable format, know who you shared it with, and withdraw consent. Each right needs a path in the product or a documented manual process, and a response within the law's timeframes. Build the obvious ones in: an export of the person's data as JSON, account deletion that actually deletes, a profile page where fields are editable, and a contact channel that is answered. Keep a record of requests and responses; accountability is a principle, and the record is its proof.

How to apply

  • Pick the basis per purpose: contract for the service, legitimate interest for security, consent only for extras.
  • Consent is granular, opt-in and revocable where you use it at all.
  • Ship export and deletion as features, not as support tickets.
  • Log requests and answers with dates.

Details that make the difference

  • Pre-checked boxes are not consent.
  • Legitimate interest needs a written balancing test you can show.
  • Deletion has exceptions: legal obligations may require keeping some records; say which.
  • Portability means a machine-readable export, JSON is fine.
  • Designate a contact (encarregado) even if it is you, and publish it.
Sources: Lei nº 13.709/2018 (LGPD), artigos 7, 11 e 18 · ANPD, materiais educativos e publicações · ICO, Guide to the data protection principles (GDPR parallel)

Privacy by Design in the Product

Privacy by design means the safe choice is the default and the private choice is real in the backend, not a toggle that hides a button. Visibility controls, deletion, retention, cookies and the privacy policy are product features, built with the same care as the wishlist itself.

Why

The LGPD asks for privacy from conception and by default. In the wishlist that means: new lists private, profile fields minimal, analytics off until the person agrees, and every "private" in the interface backed by a policy in the database and in storage. The privacy policy and the terms of use are different documents with different jobs: the policy explains what data, why, on which basis, with whom, for how long and how to exercise rights; the terms set the rules of the service. Both are read by few and matter to all; write them in plain language and keep them accurate, because a policy that promises what the system does not do is itself a violation.

Cookies get their own paragraph because the folklore is wrong. Strictly necessary cookies, the session and the preference you need to run the service, need no consent banner. Analytics and marketing do need a real choice, off by default, with the same ease to refuse as to accept; the ANPD has published guidance on exactly this. Retention closes the loop: decide how long you keep an inactive account, deleted-list data, logs and backups, and automate the deletion. Account deletion must cascade through rows, files and, within the backup window, backups too, and the person should get a confirmation. Finally, a privacy contact that answers, and a dated change log for the policy.

How to apply

  • Private by default, every visibility control enforced in the database and in storage.
  • Privacy policy and terms as separate, plain-language pages, accurate to what the code does.
  • Cookie choice only for analytics and marketing, off by default, refuse as easy as accept.
  • Retention schedule automated, deletion cascades through rows, files and backups.

Details that make the difference

  • Delete means delete: rows, storage objects, search indexes, and the backup window stated.
  • No consent banner for necessary cookies; one that blocks the page for everything is the anti-pattern.
  • The share dialog is a privacy moment: repeat what will be visible.
  • Policy versioning with dates, and notify on material changes.
  • Minimal profile: handle and display name; everything else optional.

Vendors, Incidents and the Pre-Launch Review

Supabase, Cloudflare and GitHub process your users' data on your behalf, often outside Brazil. Know their terms, know where the data lives, and have a plan for the day something goes wrong. Then run the pre-launch review: three users, every operation, every file, every header, with evidence.

Why

Operators are part of your responsibility. Read the data processing terms of each vendor, note the regions where data is stored, and record them in the inventory; the LGPD regulates international transfers and the ANPD has rules for them, so a database in a non-Brazilian region is a decision to document, not an accident. Subprocessors change: subscribe to the vendors' notices. Incidents will happen: a leaked key, a policy mistake that exposed private lists, a compromised account. The LGPD requires communicating relevant incidents to the ANPD and to affected people; the practical plan is four steps, detect, contain, assess, communicate, with the contacts, the templates and the decision criteria written before you need them.

The pre-launch review is where this whole section becomes evidence. Walk the permission matrix with a visitor, the owner and another user, through the API, for every operation, and record results. Fetch private images by URL as the wrong user. Review the auth flows, the password rules, the emails and every redirect. Check headers, CSP, HTTPS, upload limits and external URL handling. Confirm secrets are out of the repo and the bundle, dependencies are current, backups restore, alerts fire. Reread the inventory, the policy, the retention schedule and the deletion flow against what the code actually does. List the residual risks you accept and the items you postpone, with an owner and a date. Launch with that document, not with a feeling.

How to apply

  • Vendor table: what each processes, where, under which terms, with a link to the notice feed.
  • Incident plan on one page: detect, contain, assess, communicate, with contacts and templates.
  • Pre-launch review with evidence: every matrix cell tested, every check screenshot or log attached.
  • Residual risk register signed before real users arrive.

Details that make the difference

  • "Configured" is not "tested". The review tests.
  • Practice the incident plan with a tabletop exercise of a leaked key.
  • Retest after every schema or policy change, automated where possible.
  • Priority if time is short: RLS and cross-user tests, then auth, then storage and secrets, then OWASP, then LGPD documents.
  • This trail is education; it is not a certification or legal compliance. Get a review before launch.
